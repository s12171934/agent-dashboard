# agent-dashboard

Claude Code·Codex 에이전트 세션, Orca Run, `aplan` 작업 계획을 한 화면에서 실시간으로 보여 주는 웹 대시보드다.

- 세션 로그를 증분으로 읽어 상태 변화를 SSE 로 브라우저에 밀어 준다.
- 세션별 토큰·비용, 진행 중인 단계, 에이전트 사이 상호작용, 테스트 실행, 결정 대기 질문을 보여 준다.
- 서버는 Python 표준 라이브러리만 쓴다. 설치할 의존성이 없다.

## 구성

| 폴더 | 무엇 | 어디서 도는가 |
| --- | --- | --- |
| `frontend/` | 정적 페이지 (빌드 단계 없음) | Cloudflare Pages — `https://dashboard.s-dante.com` (= `agent-dashboard-2at.pages.dev`) |
| `functions/` | Pages Function `/chars/*` — 배포 없이 더한 캐릭터를 R2 버킷 `agent-dashboard-chars` 에서 읽어 준다(없으면 배포본) | 페이지와 함께 배포 |
| `design-system/` | 토큰·유리 질감·공용 컴포넌트(웹 컴포넌트·클래스). 페이지에는 `ds/` 로 붙는다 — [design-system/README.md](design-system/README.md) | 페이지와 함께 배포 |
| `server/` | 메트릭 서버 (진입점 `server.py`, 코드는 `adash/` 패키지 — 레이어·기능 구조는 [`server/adash/README.md`](server/adash/README.md). REST `/api/*` + SSE `/events`), `decision-hook`, `session-guard`, `aplan`, `launchd/` | 로컬 Mac |
| `scripts/` | `deploy-frontend.sh` — `frontend/`(+ `design-system/` → `ds/`)를 Pages 에 배포, `dev-frontend.py` — 로컬 개발 서버, `check-ds.py` — 디자인 시스템 규칙 검사, `check-flow.py` — 흐름 이탈 판정 규칙을 가짜 입력으로 확인, `check-server.py` — 서버 패키지의 레이어 의존·순환 import 검사, `char-gen.sh`·`char-sprites.py` — 캐릭터 모드 그림 생성·자르기, `char-publish.py` — 새 캐릭터를 배포 없이 R2 에 올리기 | |
| `exports/` | 공개 스키마 | |

```
브라우저 ── https://dashboard.s-dante.com (페이지)
   └─ fetch / EventSource ──► http://127.0.0.1:8787          (이 Mac)
                          └─► https://<mac>.<tailnet>.ts.net  (tailnet 기기, tailscale serve 경유)
```

- 페이지는 메트릭 서버 목록을 기기마다 따로 기억한다(기본값 `http://127.0.0.1:8787` 하나). 연결 표시(오른쪽 위 「실시간」)를 누르면 「메트릭 서버」 패널이 열리고, 켜진 서버가 하나도 연결되지 않으면 저절로 열린다. `?server=<url>` 로 열면 그 서버를 목록에 넣고 켠다.
- 서버를 여러 개 등록할 수 있다(기기마다 서버 하나씩 띄운 여러 Mac 등). 체크한 서버만 화면에 들어가고, 패널의 「보기」로 고른다.
  - **합쳐 보기:** 모든 서버의 세션·Run·테스트·결정 대기를 한 목록으로. 카드에 서버 배지가 붙는다.
  - **서버별 보기:** 에이전트 탭을 서버마다 구획으로 나눈다.
  - 비교 탭에는 「서버별」 묶음이 생긴다. 상단 합계는 켜진 서버 전체다.
  - 상세·유휴 표시·결정 응답·Orca 열기·닫기는 그 세션을 보낸 서버로 간다. 연결 안 되는 서버는 빼고 그리며, 오른쪽 위 「⚠ 오류」에 이름이 뜬다.
- https 페이지는 http 주소를 부를 수 없다(혼합 콘텐츠). 예외는 루프백뿐이라, 다른 기기에서는 `tailscale serve --bg 8787` 이 주는 https 주소를 쓴다.
- Chrome 은 공개 사이트가 로컬 주소를 부를 때 「로컬 네트워크 접근」 권한을 한 번 묻는다. 허용해야 붙는다.

## 요구 사항

- macOS (상시 실행에 `launchd` 를 쓴다. 서버 자체는 Python 3 만 있으면 된다)
- Python 3
- 선택: Orca CLI(`orca`)가 `PATH` 에 있으면 Run·터미널 정보를 함께 보여 준다

## 실행

```sh
python3 server/server.py --origin https://dashboard.s-dante.com --origin https://agent-dashboard-2at.pages.dev
tailscale serve --bg 8787                                                  # 다른 기기용 https 주소 (선택)
```

로컬에서 페이지를 고칠 때는 `python3 scripts/dev-frontend.py` 로 띄우고 `http://127.0.0.1:5500` 을 연다(`--port` 로 바꿀 수 있다). `frontend/` 의 파일을 저장하면 열린 탭이 저절로 따라온다: CSS 는 새로 고치지 않고 그 자리에서 바뀌고, 나머지는 페이지를 새로 고친다. `http://localhost:*`·`http://127.0.0.1:*` 출처는 `--origin` 없이 허용된다.

| 옵션 | 기본값 | 뜻 |
| --- | --- | --- |
| `--port` | `8787` | 수신 포트 |
| `--hours` | `24` | 이 시간 안에 갱신된 세션만 추적 |
| `--runs` | `8` | 추적할 최근 Orca Run 의 최소 개수 |
| `--host` | `127.0.0.1` | 바인드 주소. 여러 번 줄 수 있다 |
| `--origin` | 없음 | CORS 를 허용할 페이지 출처. 하위 도메인(Pages 프리뷰 배포)도 포함하므로, 다른 서비스가 사는 도메인이면 그 하위 도메인들도 허용된다. 여러 번 줄 수 있다 |
| `--vault` | `~/Obsidian/obsidian` | Obsidian 볼트. 노트를 만든 세션(`agent/` 태그)으로 묶어 세션 상세에 보여 준다. 폴더가 없으면 꺼진다 |
| `--projects-dir` | 없음 (기능 꺼짐) | 프로젝트 폴더들을 담은 폴더. 바로 아래 하위 폴더 중 `progress.json` 이 있는 것을 프로젝트로 본다. 여러 번 줄 수 있다 |
| `--design-dir` | 없음 | 설계문서 폴더. `prefs.json` 의 `design_dirs` 에 더해진다. 여러 번 줄 수 있다. 둘 다 없고 외부 계획에 `design_root` 도 없으면 「설계문서」 기능이 꺼진다 |
| `--design-days` | `14` | `--hours` 밖의 세션 로그에서 설계문서 참조를 찾는 기간(일). 한 번 읽은 로그는 바뀌기 전까지 다시 읽지 않는다 |

## 상시 실행 (launchd)

`server/launchd/install.sh` 가 템플릿(`server/launchd/agent-dashboard.plist.in`)을 채워 `~/Library/LaunchAgents/` 에 설치하고 시작한다.

```sh
DASH_ORIGINS="https://dashboard.s-dante.com https://agent-dashboard-2at.pages.dev" server/launchd/install.sh   # 설치·재설치
server/launchd/install.sh uninstall                                                                           # 중지·제거
```

| 환경 변수 | 기본값 |
| --- | --- |
| `DASH_LABEL` | `local.agent-dashboard` |
| `DASH_HOSTS` | `127.0.0.1` (공백으로 구분) |
| `DASH_ORIGINS` | 없음 (공백으로 구분, `--origin` 으로 넘김) |
| `DASH_PYTHON` | `PATH` 의 `python3` |
| `DASH_PROJECTS_DIRS` | 없음 (`:` 로 구분 — 경로에 공백이 있을 수 있어서. 각각 `--projects-dir` 로 넘김) |

예: `DASH_PROJECTS_DIRS="$HOME/notes/projects" DASH_ORIGINS="…" server/launchd/install.sh`

- 같은 포트로 손으로 띄운 서버가 있으면 먼저 내려야 한다.
- 로그는 `server/server.log` 에 쌓인다.

## 프론트 배포 (Cloudflare Pages)

main 에 `frontend/`·`design-system/`·`scripts/deploy-frontend.sh` 변경이 들어오면 GitHub Actions(`.github/workflows/deploy-frontend.yml`)가 `scripts/deploy-frontend.sh` 로 프로덕션에 배포한다. Actions 탭에서 손으로 돌릴 수도 있다(workflow_dispatch).

- 저장소 시크릿 두 개가 있어야 돈다: `CLOUDFLARE_API_TOKEN`(권한 Account · Cloudflare Pages · Edit), `CLOUDFLARE_ACCOUNT_ID`.
- Pages 프로젝트가 직접 업로드 방식이라 Cloudflare 의 Git 연동은 쓰지 않는다(직접 업로드 프로젝트는 나중에 Git 을 붙일 수 없다).

손으로 배포할 때:

```sh
npx wrangler login              # 한 번
scripts/deploy-frontend.sh      # frontend/ 를 프로덕션에 배포 (프로젝트가 없으면 만든다)
PAGES_BRANCH=dev scripts/deploy-frontend.sh   # 프리뷰 배포 (<hash>.agent-dashboard-2at.pages.dev)
DEPLOY_OUT=/tmp/adash-out scripts/deploy-frontend.sh   # 배포하지 않고 올릴 파일만 만들어 확인
```

- Pages 프로젝트에 R2 바인딩 `CHARS` → 버킷 `agent-dashboard-chars` 가 프로덕션·프리뷰 모두 걸려 있다(프로젝트 설정, 저장소에는 없음). `deploy-frontend.sh` 는 저장소 루트에서 `wrangler pages deploy` 를 돌려 `functions/` 를 함께 올린다.
- `dashboard.s-dante.com` 은 Pages 프로젝트 `agent-dashboard` 의 커스텀 도메인이다 (`dashboard` CNAME → `agent-dashboard-2at.pages.dev`, 프록시).
- PWA 로 설치할 수 있다 (`manifest.webmanifest`, `sw.js`, `icons/`). Chrome·Edge 는 주소창의 설치 버튼, iOS Safari 는 공유 → 홈 화면에 추가. 서비스 워커는 이 출처의 페이지 파일만 네트워크 우선으로 캐시해 오프라인에서도 열리게 하고, 메트릭 서버 요청과 `build.json` 은 건드리지 않는다.
- 앱 아이콘은 바의 「앱 아이콘」에서 고른다: 컨셉 5종(그리드·펄스·봇·터미널·노드) × 색 4종(블루·에메랄드·선셋·그래파이트) = 20개, 이 기기에만 저장(`adash.icon`). `icon-boot.js` 가 고른 아이콘의 manifest·파비콘·apple-touch-icon 으로 링크를 바꾼다. 탭 아이콘은 바로 바뀌고, 설치한 앱은 브라우저가 다음에 manifest 를 확인할 때 바뀐다(Chrome 은 바꿀지 물을 수 있음). iOS 는 추가할 때의 아이콘을 유지하므로 홈 화면에 다시 추가해야 한다.
- 아이콘은 `scripts/make-icons.py` 가 만든다(SVG 템플릿 → headless Chrome 으로 PNG). 기본(그리드·블루)은 `icons/` 와 `manifest.webmanifest`, 나머지는 `icons/app/<컨셉>-<색>/` 에 manifest 와 함께 있다. 아이콘을 바꾸거나 더할 때는 스크립트를 고쳐 다시 돌리고, 목록은 `icon-boot.js` 에도 맞춘다.
- 배포할 때 페이지가 이름으로 불러오는 파일(`index.html` 의 스크립트·스타일, `ds.css` 의 `@import`, `ds.js` 의 `import`, 아이콘 스프라이트 `icons.svg`)에 `?v=<build>` 를 붙인다(원본은 그대로). `dashboard.s-dante.com` zone 이 `_headers` 의 `no-cache` 를 무시하고 JS·CSS·SVG 를 4시간 브라우저 캐시로 내보내서, 새 `index.html` 이 예전 `app.js`·`app.css`·`icons.svg` 와 섞여 화면이 깨졌기 때문이다(`*.pages.dev` 주소는 `no-cache` 그대로). 근본적으로는 그 zone 의 Caching → Browser Cache TTL 을 「Respect Existing Headers」로 두면 된다. 서비스 워커는 파일을 쿼리 없이 경로로 캐시한다.
- 배포본에는 `build.json` 이 붙는다. 열려 있는 탭은 1분마다, 그리고 화면에 다시 나타나거나 포커스·네트워크를 되찾을 때마다(10초에 한 번까지) 이것을 확인해 새 배포면 서비스 워커를 갱신하고 새로 고친다. 설치한 PWA 는 다시 열기보다 백그라운드에서 돌아오는 일이 많아서다.
- 서버와 페이지는 따로 배포되므로, `/api/*` 모양을 깨는 변경은 `server/adash/http/snapshot.py` 의 `API_VERSION` 과 `frontend/api.js` 의 `API_VERSION` 을 함께 올린다. 다르면 페이지가 그리지 않고 알린다.

## 홈 — 위젯으로 모아 보기

주소에 탭이 없으면(`#` 없이 열면) 홈이 뜬다. 탭마다 흩어진 것을 위젯 격자 하나에 모으고, 사람이 손댈 것을 맨 위에 둔다. 위젯은 같은 스냅숏(`/api/state`)을 다시 그리고, 머리줄 「→」로 전체 보기가 있는 탭에 간다.

| 위젯 | 보여 주는 것 | 기본 |
| --- | --- | --- |
| 내 차례 | 결정 대기(선택지 하나짜리 질문은 버튼으로 바로 답함) · QA 막힘 · 반출 승인(커밋 완료 단계) · 입력 대기 세션. 크기만큼 줄을 보이고 나머지는 종류별 개수 | L · 고정 |
| 흐름 이탈 | 서버의 흐름 판정(`state.flow`) — 규칙·사유·근거 첫 줄. 판정을 안 보내는 서버뿐이면 숨김 | M · 고정 |
| 테스트 | 실행 중 테스트와 24시간 안에 끝난 실행·실패 | S |
| 오늘 비용 | 세션 5분 슬롯을 0시부터 시간대별로, 가장 큰 세션 | S |
| 작업 보드 | 코디네이터 묶음(Run 태스크 막대 — 30개 넘으면 비율 막대)과 워커·단독 세션의 aplan 단계. 실행·백그라운드·입력 대기·결정 대기·1시간 안의 기록·6시간 안의 응답 없음만, 「완료도 보기」로 전부 | W |
| QA 파이프라인 | QA 드라이버 단계별 티켓 수(와 막힘). 사람 관문 단계에 워크트리가 있는 티켓이 있으면 테두리. 단계를 누르면 그 단계의 티켓이 오래 머문 순으로 펼쳐지고, 줄마다 워크트리 리뷰 탭과 같은 버튼(반출 승인·PR 머지·워크트리 정리·코디네이터 재기동·VS Code 로 열기)과 작업 중이면 코디네이터 「Orca 에서 열기」. 워크트리가 없는 티켓은 「워크트리 없음」으로 표시하고 「내 차례」의 반출 승인에서 뺀다. 「외 n건」은 그 단계로 거른 워크트리 리뷰 탭 | M |
| 오늘 타임라인 | 최상위 세션을 한 시간축에(3·6·24시간), 흐름 이탈이 있는 세션은 ⚠ | M |
| 관계 미니맵 · 프로젝트 진행 · 최근 볼트 문서 · 설계문서 참조 · 서버 상태 | 「편집 → 위젯 추가」로 넣는 선택 위젯 | — |

- 「편집」: ⠿ 를 끌어 순서를 바꾸고, `S`(1칸)·`M`(2칸)·`L`(2×2)·`W`(한 줄) 로 크기를, 📌 로 맨 위 고정을, ✕ 로 빼기를 한다. 고정 위젯은 늘 고정 안 된 위젯보다 앞에 온다. 「기본값으로」는 위 기본 배치로 되돌린다.
- 배치는 이 기기에만 저장한다(`localStorage` `adash.home`: `{widgets: [{id, size, pin, opts}], fold}`) — 휴대폰과 데스크톱의 배치가 다를 수 있다.
- 휴대폰(≤500px)에서는 고정 위젯만 펼치고 나머지는 제목 줄로 접는다. 제목을 누르면 펼치고, 그 상태도 기기에 남는다. 900px 이하는 2열이다.
- 데이터가 없는 위젯(QA 묶음 없음, 테스트 기록 없음 등)은 평소에 숨고, 편집 중에만 자리를 보인다.
- 플로팅 바 「홈」의 개수 배지는 「내 차례」 건수다.

## 에이전트 탭 보기 — 코디네이터 트리 / 워크트리별 / 관계 지도 / 타임라인

에이전트 탭 맨 위의 전환으로 고른다. 이 기기에만 저장된다(`adash.agview`).

- **코디네이터 트리:** 코디네이터 아래에 워커·하위 코디네이터·드라이버를 묶는 기본 보기.
- **워크트리별:** 세션을 실행 중인 워크트리(작업 디렉터리의 워크트리 경로) 단위 구획으로 나눈다. 구획 머리에 프로젝트·워크트리·브랜치, 에이전트 수(코디네이터·워커·단독)와 상태별 수가 보이고, 「최소화」로 구획을 접을 수 있다(「모두 펼치기」·「모두 최소화」는 구획과 그 안의 묶음을 함께 연다·접는다). 서브에이전트는 부모 카드에 합쳐진다.
  - 구획 안은 코디네이터 트리와 같은 UI다: 그 워크트리에서 도는 코디네이터의 묶음(요약 줄·워커 계획·펼치기/최소화, 접힘 상태도 트리 보기와 공유)과 단독 세션.
  - 코디네이터가 다른 워크트리에서 돌리는 워커·하위 코디네이터는 그 트리 끝에 작은 블록(역할·이름·상태·▣ 워크트리, 폭은 에이전트 카드와 같음)으로 붙고, 요약 줄에 「다른 워크트리 N」이 뜬다.
  - 반대로 코디네이터가 다른 워크트리에 있는 워커는 그 코디네이터의 작은 블록 아래에 트리 선으로 묶인다.
  - 작은 블록을 누르면 실제 카드로 스크롤해 잠깐 강조한다(접힌 구획·묶음은 펼친다). 대상이 화면에 없으면(필터로 빠짐 등) 세션 상세를 연다.
  - 「실행 중만」·「Orca 에 열린 것만」은 트리 보기와 같은 규칙으로 거른다. 「서버별 보기」에서는 서버 구획 안에 워크트리 구획이 들어간다.
- **관계 지도:** 드라이버(QA 드라이버) → 코디네이터(티켓) → 워커(구현) → 리뷰·판정 네 열. 묶음 하나가 QA 드라이버 하나(그 티켓들의 코디네이터가 띠마다 하나) 또는 코디네이터 묶음 하나다.
  - 선: 실선 = 띄움(부모 → 자식, 한 줄기에서 가지로), 노랑 화살표 = 선행(Orca 태스크 deps), 보라 점선 = 최근 6시간 메시지(상호작용 탭과 같은 Orca inbox), 빨강 = 이탈 경로(목적지 노드가 이탈 bad 이거나 이탈의 근거 태스크).
  - 노드: 왼쪽 띠 = 상태 색(실패는 빨강, 완료로 세지 않음), 진행 칸 = 「QA 단계 n/9」(드라이버 상태 계약) 또는 「계획 n/m」(aplan), 워커는 「N분째 (기대 M분)」, 그리고 「✓ 흐름 정상」 또는 「⚠ 이탈 N · 이유」. 노드는 버튼이다.
  - 노드를 고르면 옆 패널(휴대폰은 아래)에 계약 대비 실제(QA 단계 칸별 들어간 시각·빠진 관문, 체크박스면 구현 → 리뷰 codex · 리뷰 claude → 판정의 그 회차 태스크별 결과), 이탈마다 근거와 「정상으로 표시」, aplan 단계, 「세션 열기」·「Orca 에서 열기」·빠진 리뷰 세션 열기가 나온다(`adash.mapsel`).
  - 수백 에이전트: 이탈 → 주의(응답 없음·입력 대기·실패) → 실행 중 순으로 묶음·띠를 놓고, 다 끝난 묶음·띠는 접힌다. 열마다 이탈·진행 중이 아닌 끝난 노드 셋 이상은 「✓ 완료 N」, 8개를 넘으면 나머지는 「외 N」, 띠 12개(묶음 40개)를 넘으면 「더 보기」. 접힘은 트리와 같은 `adash.min`.
  - QA 티켓 코디네이터·워커가 일반 터미널(단독 세션)이면 드라이버가 기록한 터미널 핸들, 없으면 제목·워크트리 이름의 티켓 키로 그 티켓 띠에 붙인다(그 회차에 처음 시작한 세션이 코디네이터). 관계가 없는 단독 세션은 이탈·주의인 것만 맨 끝 「단독 세션」 묶음에 모은다.
- **타임라인:** 코디네이터 하나(고르기, `adash.tlcoord`)와 그 아래 에이전트를 한 시간축에. 막대 = aplan 계획 단계(시작~끝), 회색 막대 = 계획을 남기지 않은 세션의 첫~마지막 기록, 점선 틀 = 기대 시간(같은 Run 의 끝난 형제 태스크 중앙값, 코디네이터 상세의 「남은 예상」과 같은 값), 빗금 = 결과 없음(판정이 기다리지 않은 리뷰)·응답 없음, 보라 점선 = 메시지, 파란 선 = 지금. 아직 오지 않은 시간은 그리지 않는다.
  - 기간 「최근 2·6·24시간 / 전체」(`adash.tlwin`, 고르지 않으면 하위 40개 이하는 전체, 넘으면 최근 6시간), 80줄까지(가장 최근에 끝난 순). 시작 전 태스크는 줄 대신 수만 적는다. 아래 카드에 이 코디네이터 아래 이탈마다 근거와 「정상으로 표시」, 정상으로 끝난 에이전트 몇 개를 적는다.
  - 단계 시각은 `/api/plans` 로 그 세션들의 계획만 가져온다(스냅숏에는 단계 상태만 있다).


## 캐릭터 모드

**캐릭터 모드** 켜기·끄기는 플로팅 바 「설정」 묶음의 토글(웃는 얼굴)이다. 나머지 캐릭터 설정은 바 ⋯ 「더 보기」 메뉴의 **「캐릭터 설정」**(그림, 휴대폰은 시트의 「설정」 묶음) 패널에 모여 있다: **그림체**(AI 생성·Live2D), **보기**(상반신·전신), 「캐릭터 그림 관리 →」(「캐릭터」 탭). 모두 이 기기에만 저장된다(`adash.charmode`·`adash.charstyle`·`adash.charframe`). 캐릭터 모드를 켜면 에이전트 탭이 카드 대신 「사무실」 그림으로 바뀐다. 다른 탭과 세션 상세는 그대로다.

- 워크트리 하나가 방 하나다(「워크트리별」 보기와 같은 기준 — 서버가 둘 이상이면 서버별로도 나뉜다). 방 안은 코디네이터·하위 코디네이터가 앞, 그다음 상태 순이다. 방 머리에 워크트리 이름·프로젝트·브랜치와 상태별 수가 보인다.
- 코디네이터 묶음마다 색이 하나씩 붙는다. 코디네이터는 그 색 칩에 「◆ 워커 N · 다른 방 M」, 워커는 「◆ <코디네이터> 소속」을 단다(툴팁에 코디네이터의 방). 워커가 다른 워크트리 방에 있으면 코디네이터에서 그 워커까지 같은 색 곡선(코디네이터 쪽 점, 워커 쪽 화살표)을 방 위로 긋고, 묶음의 첫 선 꼭대기에 「◆ <코디네이터> 의 워커」 꼬리표를 단다. 사람을 가리키면 그 묶음의 선·칩·사람만 남고 나머지는 흐려진다. 이어진 방끼리는 붙여서 놓고(최상위 코디네이터가 있는 방이 앞), 이어진 무리가 외딴 방보다 먼저 온다.
- 방은 한 장면이다: 위쪽 벽(창문·책장·시계·포스터·화이트보드, 시계는 지금 시각)과 아래 바닥. 폭에 들어가는 만큼만 벽 장식을 건다.
- 에이전트는 일본 애니메이션풍 오리지널 캐릭터 6명 중 하나다: 일반 4명(aoi·ren·hina·sora)과 헤드셋을 쓴 코디네이터 2명(kaede·yuki). 누가 될지는 세션마다 정해져 갱신해도 바뀌지 않는다. 이름표 밑줄이 모델 색이다.
- 캐릭터마다 AI 로 생성한 시트 3장 — 일러스트 **전신**·**상반신**과 **SD(2등신 치비) 픽셀** — 이 있고(SD 상반신은 SD 시트의 머리~허리를 더 촘촘한 격자로 픽셀화해 얼굴이 더 크다), 시트마다 8가지 모션이 있다(서 있기·노트북 타자·커피·머리 감싸 쥐기·졸기·브이·손 들기·눈 감은 서 있기). 상반신·전신은 두 그림체 모두에 적용된다(기본 상반신 — 작게 보아도 얼굴이 읽힌다).
- 그림체: **AI 생성**(상태에 맞는 모션을 **SD 치비 픽셀 아트**로 보여 줌 — 모두 같은 2등신 몸 — aoi 의 SD 시트를 비율 템플릿으로 나머지를 그림. 일러스트 전신 시트를 디자인 참조로 AI 가 그린 픽셀 시트를, 서 있는 포즈가 50행이 되는 격자에 맞추고 블록마다 가장 많은 색을 골라 정리, 3배 정수 확대로 굵고 또렷하게, 3px 단위로 한 칸씩 들썩임. 기본)과 **Live2D**(같은 그림을 WebGL 메시로 실시간 변형 — 호흡, 목을 축으로 한 고개 기울임, 스프링처럼 늦게 따라오는 옆머리, 몸 흔들림, 서 있을 때 눈 깜빡임). Live2D 는 숨은 WebGL 캔버스 하나로 화면에 보이는 사람만 그려 각자의 캔버스에 복사한다(브라우저의 WebGL 컨텍스트 한도에 걸리지 않음). 진짜 Cubism 리깅은 아니다.
- 상태는 모션과 말풍선 기호로 읽는다: 실행 중 = 노트북 타자(말풍선에 지금 하는 일), 백그라운드 `◍` = 커피, 입력 대기 = 서 있기, 응답 없음 `!` = 머리 감싸 쥐기·식은땀(빛바램), 유휴 `z` = 졸기(흐림), 완료 `✓` = 브이, 결정 대기 `?` = 손 들기(노란 테두리).
- **세션 상세에서도 같은 사람:** 캐릭터 모드나 홈 「사무실」을 쓰는 동안 세션 상세의 제목 옆에 사무실에서 그 세션을 맡은 사람이 같은 그림체·같은 포즈로 선다. 그 사람을 누르면 「캐릭터 고르기」가 열려 코디네이터·워커 누구로든 바꿀 수 있고, 고른 사람은 사무실에서도 그대로 보인다(`adash.chpick`, 이 기기에만 저장. 「자동으로 되돌리기」로 해시 배정에 맡김).
- 캐릭터 그림은 `frontend/chars/<이름>-<full|bust>.webp`(Live2D 용 일러스트, 프레임 8개를 가로로 이은 투명 스트립)와 `<이름>-sd.png`·`<이름>-sd-bust.png`(AI 생성 용 SD 픽셀 스트립, 전신·상반신). `scripts/char-gen.sh <이름> <full|bust|sd>` 가 Codex 이미지 생성으로 시트를 만들고(bust·sd 는 full 을 참조, aoi 외의 sd 는 aoi 의 sd 도 비율 템플릿으로 참조 — aoi 를 먼저) `scripts/char-sprites.py` 로 배경을 지워 자른다. 출력한 프레임 크기는 `app.js` 의 `CH_ART` 에 넣는다.
- **「새 캐릭터」(대시보드에서 만들기):** 「캐릭터」 탭 맨 위 상자에 원본 그림 한 장(PNG·JPEG·WebP, 10MB 까지)과 표시 이름·영문 이름·역할(워커·코디네이터)을 넣고, 생김새·요청은 골라서 적는다. 「Orca 에 맡기기」를 누르면 메트릭 서버(`POST /api/chars/create`)가 `~/.cache/agent-dashboard/chars/<영문>-<시각>/` 에 원본과 브리프(`brief.md`)를 쓰고, Orca 에 등록된 이 저장소의 메인 워크트리에 에이전트(Claude·Codex)를 띄운다. 에이전트는 원본을 보고 영어 설명(`desc.txt`, 요청이 원본보다 우선, 사람 사진이면 얼굴은 닮게 그리지 않음)을 쓰고, `CHAR_REF=<원본> char-gen.sh <영문> full` 로 전신을, 이어서 상반신·SD 를 동시에 그려 확인한 뒤 `char-publish.py` 로 올린다. 저장소 파일은 고치지 않는다.
  - 아래 목록이 작업 폴더의 파일로 진행을 보여 준다: 원본 → 설명 → 전신 → 상반신 → SD → 게시(`.published`), 그린 시트 썸네일(누르면 크게), 「Orca 에서 보기」. 도는 작업이 있으면 5초마다 다시 읽고, 게시되면 곧바로 `chars.json` 을 다시 읽어 새 캐릭터가 목록과 사무실에 나타난다. 에이전트가 포기하면 `failed.txt` 의 이유, 터미널이 결과 없이 닫히면 그렇다고 보여 준다. 끝난 작업은 「목록에서 지우기」로, 아니면 14일 뒤 저절로 지워진다(올린 캐릭터는 남는다).
  - `char-gen.sh` 의 SD 비율 템플릿(aoi 의 SD 시트)이 작업 폴더에 없으면 `scripts/char-sd-template.py` 가 `frontend/chars/aoi-sd.png` 로 다시 만든다. 파이썬은 `scripts/char-python.sh` 가 찾거나 `~/.cache/agent-dashboard/char-venv` 에 만든다(Pillow·numpy·scipy).
- **배포 없이 캐릭터 더하기:** 기본 6명은 배포본(`frontend/chars`, `CH_ART`)에 있고, 나머지는 R2 버킷 `agent-dashboard-chars` 의 `chars/chars.json` 과 그림 4장이다. Pages Function `functions/chars/[[path]].js`(Pages 프로젝트의 R2 바인딩 `CHARS`)가 `/chars/*` 를 R2 에서 먼저 찾고 없으면 배포본을 준다(`no-cache` + ETag, 바뀌지 않았으면 304). 페이지는 열 때와 빌드 확인 때마다(1분마다, 화면에 돌아올 때) `chars/chars.json` 을 다시 읽어, 바뀌었으면 그 사람들을 코디네이터·워커 목록 뒤에 붙여 다시 그린다 — 새로고침이 필요 없다. 항목의 `v`(올린 시각)가 그림 주소에 붙어, 다시 그린 사람도 바로 바뀐다. 사람이 늘면 세션이 맡는 캐릭터가 한 번 바뀔 수 있다.
  ```sh
  CHAR_DESC='young woman ..., short red hair, yellow raincoat' scripts/char-gen.sh mio full ~/chars-work   # 이어서 bust, sd (sd 는 작업 폴더의 aoi_sd.png 를 비율 템플릿으로 참조)
  scripts/char-publish.py mio --name 미오 --look '빨간 단발 · 노란 우비' --dir ~/chars-work   # 코디네이터면 --boss
  scripts/char-publish.py --list          # 올린 사람들
  scripts/char-publish.py mio --remove    # 내리기
  ```
  `char-publish.py` 는 `<이름>-full.webp`·`-bust.webp`·`-sd.png`·`-sd-bust.png` 에서 프레임 크기와 머리 위치를 재서 `chars.json` 에 적고(그림을 먼저, 목록을 마지막에 올린다), `npx wrangler login` 과 Pillow·numpy 가 필요하다. 기본 6명의 이름으로 올리면 그 사람의 그림과 크기를 덮어쓴다.
- **「캐릭터」 탭**(「캐릭터 설정」 패널의 「캐릭터 그림 관리 →」, `#chars`)이 캐릭터 그림을 관리한다. 캐릭터마다 카드 한 장에 **베이스**(AI 생성 일러스트 `.webp`) → **SD 픽셀**(`-sd.png`, 베이스 전신을 참조로 다시 그린 2등신 치비 픽셀 아트, 「AI 생성」 그림체) → **Live2D**(베이스의 실시간 변형)를 같은 포즈로 화살표로 이어 보여 준다. 아래 포즈 8개(어떤 상태에 쓰이는지 툴팁)를 누르면 세 단계가 함께 바뀌고, 상반신·전신을 고른다(`adash.chars`). 「사무실에 배치」를 끄면 그 사람은 사무실에 나오지 않고 같은 목록(코디네이터·워커)의 다른 사람이 세션을 맡는다(`adash.chpool`, 이 기기만. 한 목록을 모두 끄면 전원 배치). 「맡은 세션」은 지금 보이는 세션 중 그 사람으로 그려지는 수, 「재생성 명령 복사」는 그 그림을 다시 만드는 `char-gen.sh` 명령이다.
- 사람을 누르면 그 세션 상세가 열린다. 끌면(휴대폰은 길게 누른 뒤 끌면) 방 안 어디로든 옮겨지고, 포커스한 뒤 방향키(Shift 는 크게)로도 옮긴다. 아래로 끌면 방이 늘어난다. 옮긴 자리는 이 기기에 남는다(`adash.chpos`: 세션별 `{x: 남는 폭에 대한 비율, y: px}`) — 실시간 갱신이나 폭 변경 뒤에도 그 자리다.
- 「원래 자리로」는 옮긴 사람을 모두 처음 자리(격자)로 미끄러지듯 되돌린다. 옮긴 사람이 없으면 꺼져 있다.
- 「실행 중만」·「Orca 에 열린 것만」 필터가 그대로 걸린다.

## 흐름 이탈 판정 (서버)

서버(`flow_check`)가 스냅숏마다 판정해 `/api/state` 의 `flow` 로 보낸다. 화면은 판정하지 않고 결과를 노드·줄에 놓는다. 정상 흐름은 계약에서 읽는다: QA 단계 순서와 사용자 관문은 qa-ticket-driver 의 상태 계약(`exports/state-contract.md`, `prefs.json` `qa_contract` 로 바꿀 수 있음)의 두 표에서, 체크박스 역할은 `CHECKBOX_FLOW`(`prefs.json` `checkbox_flow` 로 바꿀 수 있음)에서, 세부 진행은 세션의 aplan 계획에서.

| 규칙 | 단위 | 판정 | 근거 데이터 |
| --- | --- | --- | --- |
| 순서 위반 | 티켓 | 사용자 관문(계약에서 쓰는 쪽이 「사용자」인 단계, 지금은 반출 승인)을 건너뛰고 다음 단계 신호가 생김 = 승인 없이 반출(bad) · 열린 PR 이 있는데 정리(bad) · 열린 PR 이 있는데 Jira 가 개발 완료 이후(warn) | QA 드라이버 신호 파일, `gh pr list` 상태, Jira 상태. PR·Jira 를 읽지 못했으면 판정하지 않는다. 신호 파일 시각(mtime)은 마지막으로 쓴 시각이라 두 신호의 앞뒤는 보지 않는다 |
| 필수 단계 누락 | 태스크(판정) | 판정이 통과로 끝났는데 그 회차의 리뷰(판정보다 먼저 만든 역할별 마지막 리뷰) 중 취소되지 않고 판정 전에 끝나지 않은 것이 있음(bad) | Orca 태스크 상태·생성·완료 시각. 그 리뷰어가 아예 없으면 판정하지 않는다 |
| 정체 | 세션 | 응답 없음(카드의 「응답 없음」과 같은 상태: 턴이 열린 채 15분 넘게 기록 없음·API 오류로 멈춤, bad) · 워커 태스크 경과가 같은 Run 의 끝난 형제(같은 역할, 같은 모델 우선) 중앙값의 2배 초과(warn). 입력 대기는 사람 시간이라 보지 않는다 | 세션 상태, `estIndex` 와 같은 형제 시간. 끝난 형제가 둘 미만이면 판정하지 않는다 |
| 반복 | 체크박스 | 같은 체크박스의 구현 → 리뷰 라운드(구현 태스크 수)가 3 이상(warn) | 태스크 이름 `<티켓>#<번호> <역할>` 과 생성 순서 |
| 계획 미이행 | 세션 | 세션이 끝났는데(완료·유휴) 마지막 aplan 계획에 남은 단계가 있음(warn) | `~/.agent-plans/<session>.jsonl` |

- 항목 모양: `{id, rule, rule_name, severity: bad|warn, unit: session|task|checkbox|ticket, reason, evidence: [문장], session, task_id, task_ids, ticket, handles}`. `flow.contracts` 에 판정에 쓴 계약, `flow.ok` 에 정상으로 표시해 뺀 수.
- 규칙을 고치면 `python3 scripts/check-flow.py` 로 규칙마다 걸리는/안 걸리는 경우를 확인한다.
- 「정상으로 표시」: `POST /api/flow/ok {"id", "ok": true}` 가 `prefs.json` 의 `flow_ok` 에 남기고, 그 이탈은 다시 뜨지 않는다(`"ok": false` 로 되돌림, 30일 지난 표시는 지운다). 화면의 토스트에서 되돌릴 수 있다.

## 코디네이터 상세 — 체크박스 흐름과 워커 표

워커·워커 계획(Orca 태스크)·드라이버 계획이 있는 세션의 상세는 오케스트레이션을 먼저 보여 준다. 그 밖의 세션은 예전 배치 그대로다.

- **요약 줄(항상):** 워커 계획 막대와 범례, 워커 수·실행 중·워커 합계 비용·남은 예상.
- **오케스트레이션(접기):** 워커가 응답 없음·입력 대기·결정 대기이거나 태스크가 실패했으면 접어 둬도 저절로 펼친다.
  - **체크박스 흐름:** 태스크 이름이 `<티켓>#<번호> <역할>` 이면 체크박스 하나가 노드 하나다. 노드 안의 점 하나는 태스크 하나이고(만든 순서, 한 회차 = 구현 · 리뷰 codex · 리뷰 claude · 판정), 노드 상태는 역할마다 가장 최근 태스크로 정한다(재시도가 통과한 실패는 빨갛지 않다. 취소된 태스크는 「취소」). 티켓 단위 태스크(착수 시트·통합 리뷰 …)는 역할과 선행이 같은 것끼리 한 노드다. 티켓마다 한 줄이고, 줄 안의 노드는 deps 순서로 흐르다 폭에 맞춰 줄바꿈하며, 화살표는 노드 사이 deps 다. 이름이 이 꼴이 아니면 태스크 하나가 노드 하나다.
  - 줄 머리를 누르면 그 티켓을 접고 편다(기본: 다 끝난 티켓은 접힘). 줄 앞쪽에 끝난 노드가 둘 이상 이어지면 「✓ 완료 N」 하나로 묶고, 누르면 펼친다.
  - 노드를 누르면 오른쪽 패널(좁은 화면에서는 아래)에 단계별 워커(상태·모델·소요·비용, 누르면 세션 상세)가 나오고, 아래 워커 표가 그 노드의 세션으로 걸러진다. 고르지 않았을 때 패널은 주의가 필요한 노드를 모아 보여 준다.
  - 「시간 추이」는 계획·생성·완료의 계단선이다(접힘).
  - 드라이버 사전 계획이 있으면 그 계획(티켓 의존 그래프 포함)이 이어서 나온다.
  - **워커 표:** 직속 워커를 한 줄씩(상태·모델·소요·턴·비용). 「진행 중 · 주의 · 완료 · 전체」 중 하나와 이름 검색으로 거르며, 기본은 진행 중이라 끝난 워커는 고를 때만 보인다.
- **이 세션 지표 · 로그(접기, 기본 접힘):** 머리줄에 턴·컨텍스트·비용·압축과 로그 건수가 보인다.
- 기기별 저장값: `adash.dsec` (세션별 구획 열림), 티켓 줄과 완료 묶음의 접힘은 트리와 같은 `adash.min`.

## 새 에이전트 — 대시보드에서 워크트리·워커를 띄우고 프롬프트 보내기

바의 ＋(「새 에이전트」)가 여는 패널에서 메트릭 서버가 도는 Mac 의 Orca 로 에이전트를 띄우거나, 돌고 있는 에이전트에 말을 넣는다. 서버가 둘 이상 켜져 있으면 어느 서버(Mac)에 띄울지 고른다.

| 모드 | 하는 일 (Orca CLI) |
| --- | --- |
| 새 워크트리 | 고른 저장소에 새 워크트리를 만들고(기본 브랜치에서 새 브랜치, 부모 없음, setup 훅 실행) 그 안에 에이전트를 띄운다 — `orca worktree create --no-parent --setup run --agent …` |
| 기존 워크트리 | 이미 있는 워크트리에 에이전트 탭을 하나 더 띄운다(워커) — `orca agent launch --worktree …` |
| 프롬프트 보내기 | Orca 터미널에 연결된 에이전트를 골라 글을 입력하고 Enter 를 누른다 — `orca terminal send --enter --wait-submit 5` |

- 에이전트는 Claude 또는 Codex. 모델·effort 를 비우면 그 에이전트의 기본값이다. 모델 id 는 그 CLI 에 그대로 넘어간다.
- 에이전트는 채팅이 아니라 터미널로 띄운다(`--surface terminal`). 대시보드가 세션을 터미널로 따라가고 프롬프트도 터미널로 보내기 때문이다.
- 탭 이름(비우면 워크트리 이름)으로 Orca 탭 이름을 바꾼다. 에이전트가 스스로 터미널 제목을 바꾸면 그것이 이긴다.
- 첫 프롬프트를 비우면 에이전트만 띄운다. 띄우기는 서버 뒤에서 돌고(setup 훅이 길 수 있음) 페이지는 `/api/orca/job` 으로 결과를 받는다. 끝나면 토스트의 「Orca 에서 열기」로 그 탭으로 간다.
- 프롬프트는 세션 페이지의 「프롬프트」 버튼으로도 연다(그 세션이 골라져 있다). 서버는 지난 스냅숏이 세션에 연결한 터미널과 자기가 띄운 터미널에만 보낸다. 에이전트가 응답 중이면 입력만 들어가고 지금 턴이 끝난 뒤 읽는다(화면에 그렇게 알린다). 응답이 없을 때 다시 보내지 않는다 — 두 번 들어갈 수 있다.
- 워크트리 이름은 영문·숫자·`.-_` 60자까지(브랜치 이름이 된다). 같은 저장소에 같은 이름이 있으면 거절한다.

## 결정 버튼 — AskUserQuestion 을 터미널과 대시보드 양쪽에서 답하기

`server/decision-hook` 은 AskUserQuestion 에 거는 Claude Code PreToolUse 훅이다. 질문을 메트릭 서버에 등록하고 아무것도 출력하지 않은 채 바로 끝난다. 그래서 터미널에는 평소처럼 선택기가 뜨고, 대시보드에는 같은 질문이 카드로 뜬다. 어느 쪽에서 답해도 된다.

```json
{"hooks": {"PreToolUse": [{"matcher": "AskUserQuestion",
  "hooks": [{"type": "command", "command": "<저장소>/server/decision-hook", "timeout": 10}]}]}}
```

- 터미널에서 답하면 트랜스크립트에 그 호출의 결과가 생기고, 서버가 카드를 치운다. 터미널에서 Esc 로 취소하거나 세션이 끝나도 마찬가지다.
- 세션에 연결되지 않은 카드(세션 id 가 없거나, 서버가 추적하는 Claude 세션 중에 그 세션이 없는 것 — 화면에 「세션 목록에 없음」으로 뜨던 것)는 닫힌 질문으로 보고 90초 뒤 치운다. 90초는 막 시작한 세션의 트랜스크립트를 스캔이 잡을 시간이다.
- 대시보드에서 답하면 서버가 그 세션의 Orca 터미널에 키 입력(`orca terminal send`)으로 같은 답을 넣는다. 터미널은 훅이 넘긴 `ORCA_TERMINAL_HANDLE` 로 찾고, 없으면 대시보드가 세션에 연결해 둔 터미널을 쓴다.
- 키를 보내기 전과 매 단계 뒤에 터미널 화면(`orca terminal read --screen`)을 읽는다. 이 질문의 선택기가 처음 상태로 떠 있을 때만 시작하고, 화면이 예상과 다르면 그 자리에서 멈춘다. 선택기에 Esc 는 보내지 않으므로 질문은 터미널에 남는다.
- 대시보드에서 넣을 수 있는 답: 단일 선택, 여러 질문, 여러 개 고르기, 단일 선택의 「직접 입력」. 서버는 여러 개 고르기의 직접 입력(하나)도 받지만, 카드에는 아직 그 입력 칸이 없다.
- 대시보드에서 답할 때 터미널에 선택기가 아예 없으면(이미 답했거나 취소했는데 트랜스크립트가 아직 따라오지 못한 것) 닫힌 질문으로 보고 카드를 치운다. 다른 질문의 선택기가 떠 있으면 화면을 잘못 읽었을 수도 있어서 카드를 남기고 아래처럼 알린다.
- 카드가 「— 터미널에서 답하세요」라고 알리는 경우: Orca 밖 세션이라 터미널을 못 찾을 때, 선택기가 화면에 없거나 터미널에서 이미 답하기 시작했을 때, 키 입력이 예상대로 반영되지 않았을 때. 줄바꿈이 든 직접 입력처럼 키로 넣을 수 없는 답도 거절한다. 이렇게 오류가 난 카드에는 「카드 삭제」가 나타나 대시보드에서 치울 수 있다(터미널의 선택기는 그대로).
- 키 입력 흉내라서 Claude Code 선택기의 화면 모양·키 조작이 바뀌면 깨질 수 있다(v2.1 에서 확인). 그때도 터미널 선택기는 그대로 쓸 수 있다.
- 메트릭 서버에 닿지 않으면 훅은 바로 비켜선다. 터미널 선택기만 뜬다. 메일함 모드가 켜져 있어도 마찬가지다.
- 환경 변수: `DASH_URL` (기본 `http://127.0.0.1:8787`).

### 결정 대기 화면 (`#decide`)

헤더의 「결정 대기」를 누르면 들어간다. 모든 서버의 대기 중인 질문을 카드로 모아 보여 주고(세션 이름과 세션으로 가는 링크, 서버가 둘 이상이면 서버 배지, 대기 시간), 카드에서 바로 답하는 경로는 위와 같다. 그 아래에 메일함이 따로 보인다. 헤더 숫자는 대기 중인 질문 수이고, 안 읽은 메일함 항목이 있으면 그 수가 강조색 값으로 옆에 붙는다(「1 · 2 / 결정 대기 · 메일」).

### 메일함 모드 — 자리를 비운 동안

결정 대기 화면 위의 「메일함 모드」 버튼(또는 바의 메일 아이콘, 켜져 있으면 강조색으로 채워진다)으로 켜고 끈다. 전역 스위치 하나이고, 서버가 `prefs.json` 의 `decision_inbox` 에 보관하므로 모든 기기가 같은 상태를 보고 서버를 다시 띄워도 유지된다. 여러 서버를 켜 둔 페이지에서는 켜진 서버 모두에 같이 적용되고, 모두 켜져야 「켜짐」으로 보인다.

- 켜져 있으면 훅이 질문을 등록할 때 서버가 카드를 띄우지 않고 메일함(`server/inbox.json`)에 쌓은 뒤 `{"deny": 사유}` 로 답한다. 훅은 이것을 PreToolUse `permissionDecision: "deny"` 로 내보내므로 터미널 선택기는 뜨지 않고, 에이전트는 사유를 답 대신 읽는다.
- 사유: 사용자가 자리를 비워 질문을 메일함에 남겼으니 AskUserQuestion 을 다시 부르지 말고 각 질문의 권장 선택지(라벨에 `(Recommended)`·`(권장)`·`(추천)` 이 붙은 것, 없으면 첫 번째)나 가장 합리적인 판단으로 진행하라, 그리고 고른 답을 `[메일함 <항목 id>] 1) 답 / 2) 답` 형식의 한 줄로 남겨라. 서버가 고른 권장 선택지도 함께 적어 준다.
- **에이전트가 진행한 선택을 아는 법:** 서버는 세션 트랜스크립트의 assistant 글에서 `[메일함 <id>] …` 줄을 찾아 그 항목의 「에이전트가 진행한 선택」으로 보여 준다. 그 줄이 아직 없으면(또는 에이전트가 규약을 따르지 않으면) 서버가 질문을 받을 때 정해 둔 권장 선택지를 「권장안으로 진행」으로 보여 준다 — 추정이라는 뜻이다.
- 메일함 항목에서 다른 답을 고르고 「세션에 바꾸라고 알리기」를 누르면, 서버가 그 세션의 Orca 터미널에 `[대시보드 메일함 <id>] 앞서 X (으)로 진행했지만 사용자는 「질문」에 Y 를 골랐습니다. 반영하세요.` 한 줄을 보내고 Enter 를 누른다(`orca terminal send --enter`). 고르지 않은 질문은 메시지에서 빠진다. 에이전트가 진행한 답(남긴 줄이 없으면 권장안)과 같은 답이면 보내지 않고 「확인」을 누르라고 알린다. 터미널은 결정 버튼과 같은 방법으로 찾고, 못 찾으면 카드에 「세션에 직접 알려 주세요」라고 알린다. 보내고 나면 그 항목은 메일함에서 지워진다(세션 붙잡기도 풀린다). 보내지 못한 항목에는 「메일함에서 삭제」가 나타난다.
- 「확인」은 읽음 처리만 한다(「안읽음으로」로 되돌릴 수 있다). 메일함은 최근 200건까지 두고, 읽은 항목은 14일 뒤 지운다.
- 꺼져 있을 때는 위 결정 버튼 동작 그대로다.

**메일함 항목이 있는 세션은 붙잡아 둔다.** 사용자가 나중에 다른 답을 고르면 그 세션에 후속 메시지를 보내야 하기 때문이다.

- 서버의 세션 스캔은 `--hours` 와 상관없이 그 세션을 계속 읽는다. 그래서 메일함 카드가 「세션 목록에 없음」이 되지 않는다. 스캔이 트랜스크립트를 한 번 다 읽은 뒤에도 서버가 모르는 세션(세션 id 가 없거나 트랜스크립트가 없는 것)의 항목은 90초 뒤 지운다.
- 세션이 Orca 오케스트레이션의 워커이면, 서버가 항목을 받을 때 `orca orchestration worker-retain --dispatch <id>` 로 그 워커 터미널을 붙잡아 둔다(Run 이 끝나도 놓아주지 않게).
- 에이전트·코디네이터가 그 세션을 닫지 못하게 하는 Bash 가드 훅 `server/session-guard` 가 있다. 명령에 `orca` 가 들어 있으면 서버(`/api/decision/guard`)에 물어, 붙잡힌 세션을 닫는 명령이면 PreToolUse deny 로 막는다. 대상 명령은 `orca terminal close`(`--terminal` 이 없으면 자기 터미널, `--worktree … --all` 은 워크트리로 비교), `orca worktree rm --worktree …`, `orca orchestration worker-stop|worker-release|worker-abandon --dispatch …` 다. 워크트리 선택자는 넉넉하게 비교한다 — 잘못 막아도 사람이 대시보드에서 닫으면 된다. 서버에 닿지 않으면 비켜선다. deny 사유에서도 세션을 닫지 말라고 일러 둔다.
- 사람은 지금처럼 대시보드의 「닫기」로 닫을 수 있다.
- 붙잡는 기간은 항목이 메일함에 있는 동안이다(읽은 항목은 14일 뒤 지워진다).

```json
{"hooks": {"PreToolUse": [{"matcher": "Bash",
  "hooks": [{"type": "command", "command": "<저장소>/server/session-guard", "timeout": 10}]}]}}
```

| 엔드포인트 | 요청 → 응답 |
| --- | --- |
| `POST /api/decision/ask` | 훅이 보냄. `{"session_id", "tool_use_id", "cwd", "terminal", "questions"}` → `{"id"}`. 메일함 모드면 `{"id", "inbox": true, "deny": 사유}` |
| `POST /api/decision/answer` | `{"id", "answers"}` (질문 순서, 라벨이나 직접 입력, 여러 개 고르기는 라벨 목록) → 200 터미널 선택기에 넣음 · 400 답 누락·넣을 수 없는 답 · 409 닫힌 질문·터미널 사용 불가 · 410 `{"closed": true}` 터미널에 선택기가 없어 카드를 닫음 · 502 Orca 실패 |
| `POST /api/decision/release` | `{"id"}` → `{"ok": true}` (예전 페이지 호환, 하는 일 없음) |
| `POST /api/decision/dismiss` | `{"id"}` → 카드를 닫음(터미널 선택기는 그대로). 200 · 409 이미 닫힘 |
| `GET /api/decision/mode` | `{"inbox": 켜짐 여부}` |
| `POST /api/decision/mode` | `{"inbox": true\|false}` → `{"ok": true, "inbox"}` |
| `POST /api/decision/inbox` | `{"id", "action": "read"\|"unread"\|"delete"\|"answer", "answers"}` — `answer` 는 질문 순서대로, 그대로 둘 질문은 `null`. 200 · 400 고른 답 없음·진행한 답과 같음 · 404 없는 항목 · 409 Orca 터미널 없음 · 502 Orca 실패 |
| `POST /api/decision/guard` | `session-guard` 가 보냄. `{"command", "terminal", "cwd"}` → 메일함 항목이 있는 세션을 닫는 명령이면 `{"deny": 사유}`, 아니면 `{}` |
| `GET /api/state` 의 `decisions` | `{"available", "pending": [카드], "inbox_mode", "inbox": [항목, 최신순]}`. 메일함 항목은 카드 필드에 `recommended`(질문마다 권장 라벨), `chosen`(에이전트가 남긴 줄 또는 `null`), `read` 가 붙는다 |

## aplan — 작업 계획 기록

에이전트가 여러 단계 작업을 시작할 때 단계를 기록하면, 대시보드가 세션 카드에 단계 차트로 그린다.

```sh
aplan set "단계 1" "단계 2" ...   # 계획 기록 (1단계 시작)
aplan add "단계" [...]            # 단계 추가
aplan done [N] [메모]             # N단계 완료 (기본: 진행 중인 단계), 다음 단계 시작
aplan start N                     # N단계를 명시적으로 시작
aplan skip N [메모] / aplan fail N [메모]
```

- 호출한 세션은 `CLAUDE_CODE_SESSION_ID` · `CODEX_THREAD_ID` · Orca 터미널 핸들 순으로 식별한다.
- 기록은 출력만 하는 명령이다. 실패해도 에이전트의 본 작업을 멈추지 않는다.

## 세션이 만든 볼트 문서

볼트 노트 규칙은 모든 노트의 프론트매터 `tags` 에 그 노트를 처음 만든 세션 태그 `agent/<도구>-<세션 ID>`(`claude`·`codex`)를 하나 단다. 서버는 5초마다 `--vault` 아래 `.md` 를 훑어(점으로 시작하는 폴더 제외, mtime 이 바뀐 파일만 앞 8KB 를 다시 읽음) 이 태그로 세션별 노트 목록을 만든다.

- `GET /api/session` 응답에 `vault_on`(기능 켜짐)과 `vault_notes` 가 붙는다 — `[{"path"(볼트 기준), "abs", "title", "created", "updated", "mtime", "steps": [{"project", "dir", "path", "title", "status", "no", "stage"}]}]`, 최근 수정 순.
- `steps` 는 그 노트가 속한 프로젝트 스텝이다: 노트가 스텝 노트 자신이거나, 스텝 노트 본문이 `[[링크]]` 로 가리키는 같은 프로젝트 폴더 안 노트면 그 스텝. `_index.md`, `rules/` 아래 노트, 다른 스텝 노트로의 링크는 소속으로 치지 않는다. `--projects-dir` 의 프로젝트만 본다.
- 세션 상세의 「볼트 문서」 상자가 이를 그린다. 제목은 Obsidian 에서 열리고, 스텝 칩을 누르면 「프로젝트」 탭에서 그 프로젝트를 펼쳐 스텝 노트를 연다.
- 서브에이전트는 부모 세션 ID 로 태그를 다므로 부모 세션 쪽에 나온다.
- `GET /api/vault/recent?limit=N`(기본 10, 최대 50) — 에이전트 태그가 붙은 노트 전체에서 최근 수정 순 N개: `{"on", "notes": [{"path", "abs", "title", "mtime", "agent", "session"(이 서버가 아는 세션이면 로그 경로, 아니면 null), "session_title"}]}`. 홈의 「최근 볼트 문서」가 쓴다.

## 프로젝트 진행 API

`--projects-dir` 를 주면 그 폴더 바로 아래 하위 폴더 중 `progress.json` 이 있는 것을 프로젝트로 읽는다(조회 전용, 파일을 쓰지 않는다). 파일 형식은 `exports/project-progress.schema.json` 이고, 파일에는 원천 사실만 있으므로 아래 파생값은 모두 서버가 계산한다. 2초마다 mtime 을 보고 바뀐 파일만 다시 읽는다.

| 엔드포인트 | 응답 |
| --- | --- |
| `GET /api/projects` | `{"enabled", "version", "dirs": [{"dir", "error"}], "projects": [...]}` — 프로젝트마다 아래 필드, 단계(`stages`)에는 `steps` 를 빼고 |
| `GET /api/project?name=<폴더 이름>[&dir=<--projects-dir>]` | 프로젝트 하나, 단계마다 `steps` 포함. 같은 이름이 두 `--projects-dir` 에 있으면 `dir` 로 고르고, 없으면 먼저 준 폴더의 것. 없으면 404 |
| `GET /api/project/note?name=<폴더 이름>&path=<노트 경로>[&dir=]` | 프로젝트 폴더 안 노트 하나: `{"project", "path", "abs", "mtime", "content", "links": [{"target", "path"}]}`. `path` 는 프로젝트 폴더 기준(step 의 `path` 그대로). 스텝 노트가 아니어도 그 폴더 안 `.md` 면 준다 — 노트의 `[[링크]]` 를 따라갈 수 있게. `links` 는 본문의 위키링크를 같은 폴더 안 노트로 푼 것(볼트 경로면 뒤쪽이 가장 길게 맞는 것, 이름만이면 파일 이름으로; 폴더 밖이면 `null`). 실제 경로(symlink·`..` 해석 후)가 폴더 밖이거나 `.md` 가 아니면 404, 1MB 초과는 413 |
| `GET /events` | 기존 `data: <version>` 메시지와 별도로, 프로젝트가 바뀌면 이름 붙은 이벤트 `event: projects` / `data: <version>` 을 보낸다. 연결 직후 한 번 보낸다. `onmessage` 만 듣는 페이지는 깨우지 않는다 |

대시보드의 「프로젝트」 탭(바의 흐름 아이콘)이 이 API 를 그린다. 켜진 메트릭 서버 중 `--projects-dir` 로 띄운 서버의 프로젝트를 모두 모은다.

- **프로젝트별:** 프로젝트마다 단계를 단계 순서대로 한 줄로 잇는다. 프로젝트를 누르면 그 자리에서 펼쳐져(아코디언, 한 번에 하나) 단계와 스텝이 나온다. 단계 노드를 누르면 그 단계로 간다.
- **전체 시계열:** 굵은 줄기 하나에서 프로젝트마다 가지가 갈라진다. 날짜가 있는 사건마다 같은 간격의 칸을 주고(실제 날짜 간격에 비례하지 않음), 같은 날 끝난 단계는 나란히, 진행 중인 단계는 시작일부터 오늘까지 막대로 그린다. 모든 단계가 끝난 프로젝트는 줄기로 합류하고, 그 자리는 뒤에 갈라지는 가지가 다시 쓴다. 가로(시간 좌→우)·세로(위→아래)·자동(창 비율)으로 바꿀 수 있다. 프로젝트를 누르면 그 가지가 강조되고 상세가 그래프 아래(가로) 또는 옆(세로)에 나온다.
- **스텝을 누르면** 상세가 둘로 나뉘어 한쪽에 스텝 목록, 다른 쪽에 그 스텝의 Obsidian 노트(속성, 본문)가 나온다. 문서 자체는 Obsidian 에서 열린다: 스텝 줄의 「Obsidian」, 노트 제목, 「Obsidian 에서 열기」, 본문의 `[[링크]]`(프로젝트 폴더 안 노트는 `obsidian://open?path=<절대 경로>`, 폴더 밖은 Obsidian 검색).
- 가로로만 넘치는 영역(가로 그래프, 단계 줄)은 세로 휠로 가로 스크롤한다. 양 끝에서는 페이지가 스크롤된다.
- 기기별 저장값: `adash.proj` (보기, 방향).

`--projects-dir` 를 주지 않으면 `/api/projects` 는 `{"enabled": false, ...}`, `/api/project` 는 404, `projects` 이벤트는 나가지 않는다.

프로젝트 필드 (예: 폴더 `Sample App`)

```json
{"name": "Sample App", "dir": "/…/projects", "path": "/…/projects/Sample App/progress.json", "mtime": 1760000000.0,
 "error": null, "template": "basic", "generated_at": "2026-10-18T09:00:00+09:00",
 "status": "active", "total": 6, "counts": {"scheduling": 1, "pending": 1, "active": 1, "done": 2, "failed": 1},
 "ratio": 0.3333, "start": "2026-10-01", "end": "2026-10-20", "stage_count": 4,
 "current": {"no": 2, "name": "Build", "status": "active"},
 "stages": [{"no": 1, "name": "Design", "status": "failed", "total": 2, "counts": {…}, "ratio": 0.5,
             "start": "2026-10-01", "end": "2026-10-04",
             "steps": [{"path": "1 Design/spec.md", "title": "spec", "date": "2026-10-01", "endDate": "2026-10-03", "status": "done"}, …]}, …]}
```

- 파일을 읽지 못하거나 스키마에 맞지 않으면 그 프로젝트만 `error`(요약)와 `problems`(위반 목록)를 갖고 파생값 필드가 없다. 서버와 다른 프로젝트는 그대로 돈다. 열지 못한 `--projects-dir` 는 `dirs[].error` 에 뜬다.
- 검사하는 것: 스키마의 필수 키·알 수 없는 키·타입·`schemaVersion` 1·빈 문자열·`no` ≥ 1·`status` 값·`date`(YYYY-MM-DD)·`generatedAt`(RFC 3339)·`scheduling` 이면 날짜 없음, 아니면 `date` 있음. 설명에 적힌 것도 검사한다 — `no` 중복, 파일 안 `path` 중복, `project` 가 폴더 이름과 같음.

파생 규칙

- **단계 순서:** `no` 오름차순 (파일 안 순서가 아니라). 단계 안의 `steps` 는 순서가 의미 없다는 스키마에 따라 `date` 순(날짜 없는 것은 뒤), 같으면 `path` 순으로 준다.
- **step `title`:** `path` 의 파일 이름에서 확장자를 뺀 것 (스키마: 「Its title is the step name」).
- **개수·진행률:** `total` 은 단계의 step 수, `counts` 는 상태별 수, `ratio` = `done` / `total` (step 이 없으면 `null`). 프로젝트 값은 모든 단계의 step 을 합쳐 같은 식으로 낸다(단계 평균이 아니다).
- **기간 `start`/`end`:** 날짜가 있는 step 중 가장 이른 `date` 와 가장 늦은 `endDate`(없으면 그 `date` — 하루짜리). `pending` 의 계획 날짜와 `active` 의 「지금까지 일한 마지막 날」도 그대로 포함한다. 날짜 있는 step 이 없으면 `null`.
- **단계 상태** (step 상태들로, 위에서부터 처음 맞는 것. 프로젝트 `status` 도 모든 step 에 같은 규칙):
  1. `empty` — step 이 없다
  2. `done` — 모두 `done`
  3. `failed` — 모두 끝났는데(`done`/`failed`) 하나 이상 `failed`
  4. `active` — `active` 가 있거나, 끝난 step 과 남은 step(`pending`/`scheduling`)이 섞여 있다
  5. `pending` — 시작한 것은 없고 `pending` 이 있다
  6. `scheduling` — 모두 `scheduling`
- **현재 단계 `current`:** `active` 인 단계 중 `no` 가 가장 작은 것. 없으면 끝난 step 이 있는 마지막 단계 다음에서 처음 나오는 `pending`/`scheduling` 단계(끝난 step 이 하나도 없으면 처음부터). 그것도 없으면 `null`.

스키마에 근거가 없어 서버가 정한 것: 단계 상태 6가지와 그 우선순위(`empty` 추가, `done`·`failed` 가 섞인 채 끝난 단계는 `failed`, 일부만 끝나고 진행 중인 step 이 없는 단계도 `active`), `failed` step 을 진행률 분자에 넣지 않음, 계획 날짜를 기간에 포함, 현재 단계 고르는 법(앞 단계가 `scheduling` 으로 남아 있어도 뒤 단계가 진행 중이면 그쪽 — 단계가 순서대로만 진행되지 않는 실제 파일이 있어서), `endDate` < `date` 는 검사하지 않음.

## 설계문서 — 문서 보기와 세션의 섹션 참조

설계 폴더의 문서를 대시보드에서 읽고, 구현 세션이 문서의 어느 `##` 섹션을 읽었는지 세션 로그에서 찾아 문서·세션·티켓 화면에 보여 준다. 문서 원문과 참조 기록은 메트릭 서버에만 있다(배포되는 페이지에는 없다).

**문서 색인.** `design_dirs`(또는 `--design-dir`)의 폴더마다, 그 폴더가 든 git 저장소의 다른 워크트리(`git worktree list`)에서 같은 상대 경로의 폴더도 함께 읽는다 — 기능 설계는 대개 머지 전까지 브랜치에만 있다. 외부 계획의 `design_root` 는 설정 폴더와 이름이 같은 조상 폴더(없으면 그 부모)를 같은 방식으로 더한다. 문서는 폴더 이름부터의 상대 경로(`feature-designs/<기능>/<파일>`)로 부르므로 워크트리마다 있는 사본이 한 문서가 된다. 보여 주는 사본은 설정 폴더의 것, 없으면 가장 최근에 고친 것이다. 문서 이름은 기능 폴더의 `index.html` 뷰어와 같게 붙인다: 제목은 첫 `# ` 제목에서 앞의 자기 경로·파일 이름(`flows/A-x `)을 뺀 것이고, `index.html` 의 `SECTIONS` 목록에 든 문서는 챕터 번호·제목과 읽는 순서도 갖는다(`index.html` 도 문서처럼 설정 폴더 → 최근 수정 사본 순으로 고른다). 5초마다 mtime 을 보고 바뀐 것만 다시 읽는다.

**섹션.** `##` 제목 하나가 섹션 하나다(코드 블록 안은 제외). 제목 줄부터 다음 `##` 앞 줄까지이고, 첫 `##` 앞은 「머리말」(`##` 이 없으면 「본문」)이다. 섹션 번호는 제목 앞의 숫자(`5. 도메인 모델` → `5`)다.

**참조 추적.** 서버가 세션 로그를 읽을 때 설계 폴더를 가리키는 도구 호출을 잡아, 그 결과가 오면 읽은 줄 범위를 섹션에 대응시킨다. 한 호출이 섹션 여럿에 걸치면 섹션마다 하나씩 기록하고, 섹션에서 읽은 줄의 비율을 `cover` 로 둔다.

| 도구 | 읽는 값 | 종류 | 정확도 |
| --- | --- | --- | --- |
| Claude `Read` | `file_path`, 결과의 줄번호(`offset`·`limit` 이 정한 범위, 잘린 결과는 마지막 줄까지) | read | 정확 |
| Claude `Grep` | 결과의 `파일:줄` (줄번호 없는 모드는 같은 패턴을 그 파일에 다시 돌림) | search | 정확 / 재실행 |
| 셸 (Claude `Bash`, Codex `exec_command`·`shell`, Codex `exec` 스크립트 안의 `cmd`) | `sed -n a,bp` · `head` · `tail` · `cat` · `nl` · `awk 'NR>=a && NR<=b'` 와 뒤에 붙은 `sed -n`·`head`·`tail` 필터, `grep`·`rg` 결과의 `파일:줄`. `NAME=값` 변수와 `cd` 는 따라간다 | read / search | 근사 |

- 섹션 고정: 결과(Read 의 본문, 읽기 하나뿐인 셸 명령의 출력)에 든 `##` 제목 줄을 먼저 쓰고, 없으면 줄번호를 지금의 목차에 맞춘다. 문서가 읽은 뒤 고쳐져도 제목이 남아 있으면 맞는 섹션에 붙는다. 지금 목차에 없는 제목은 옛 제목 그대로 남아 「현재 목차에 없는 섹션」에 나온다.
- 경로: 워크트리마다 다른 절대 경로를 문서 키로 바꾼다. 경로 안에 설정 폴더 이름(`/feature-designs/`)이 있으면 된다.
- 잡지 않는 것: `grep '^## '` 같은 목차 조회, 반복문 변수(`for f in …; do sed … "$D/$f"`)·풀지 못한 변수·명령 치환, `python3`·`node` 같은 스크립트 안의 읽기, `git show <커밋>:<경로>`, 여러 파일을 이은 파이프, 서브에이전트에 넘긴 지시(서브에이전트 자신의 로그는 따로 잡힌다). 세션마다 그 수를 `design-refs.json` 의 `sessions.<id>.stats` 에 센다.
- 실측(2026-10-19, 한 사용자의 지난 14일 로그: 설계 폴더를 읽은 세션 962개, 문서 447개, 참조 63,750건, 처음부터 쌓는 데 약 30초):
  - `Read` 199회 중 192회 기록(나머지 7회는 색인하지 않는 `.html`). 46회를 결과 줄번호와 대조해 읽은 줄이 모두 섹션에 배정됐다.
  - 읽기 하나뿐인 셸 명령 669회의 출력 첫 줄을 파일과 대조: 499회는 그 줄 그대로, 123회는 읽은 뒤 문서가 고쳐져 줄이 옮겨졌거나 내용이 바뀜, 32회는 출력이 잘려 비교 불가, 15회는 확인한 예가 모두 문서 수정 탓이었다. 해석 자체가 틀린 예는 찾지 못했다.
  - 섹션 고정: 출력에 `##` 제목이 든 셸 읽기 278회 중 85회(31%)는 줄번호만으로 정했다면 다른 섹션에 붙었을 것을 제목으로 바로잡았다(Read 는 44회 중 18회).
  - 설계 경로가 든 셸 호출 7,627회(Claude) · 2,076회(Codex) 중 참조를 남긴 것은 5,070회 · 1,444회. 나머지는 대부분 읽기가 아닌 명령(`ls`·`wc`·`git`·쓰기)이고, 따라가지 못한 것은 765회(풀지 못한 변수 193 · `python3`/`node` 스크립트 208 · `sed` 편집 스크립트 120 · 파이프 뒤 필터 45 · 반복문 30 · `git show` 15 · 그 밖), 목차 조회로 뺀 것은 1,047회다.
  - 티켓: 참조를 남긴 세션 962개 중 152개에 티켓이 붙었고, 제목에 패키지 이름이 있는 80개는 모두 그 티켓과 같았다. 서브에이전트 로그 26개도 따로 잡혔다.
- 기록 `{session, ticket, doc, section, kind, cover, lines, hits, tool, exact, commit, ts, call}` 은 `server/design-refs.json` 에 남는다(세션이 `--hours` 밖으로 나가도). `ticket` 은 외부 계획의 티켓 세션 행(`task_id`)과 세션 브리프의 태스크 ID 로 붙이고, 서브에이전트는 부모의 것을 쓴다. `commit` 은 그 티켓 계획의 `design_root` 아래 문서일 때 `design_commit` 이다.

대시보드의 「설계문서」 탭(바의 책 아이콘)이 이것을 그린다. 켜진 메트릭 서버 중 설계 폴더를 색인하는 서버의 문서를 모두 모은다(여러 서버면 트리가 서버별로 나뉜다).

- **배치:** 넓은 화면에서는 페이지가 움직이지 않고 문서 본문만 스크롤된다. 위 요약 줄, 왼쪽 상자, 문서 머리, 오른쪽 목록은 제자리에 있고, 문서 목록과 오른쪽 목록은 각자 안에서 스크롤된다. 폭 900px 이하에서는 페이지 전체만 스크롤된다: 페이지에는 문서만 두고, 상자 안 스크롤을 없애려고 표와 코드는 줄을 바꿔 보인다. 플로팅 바 오른쪽의 작은 책 버튼(옆에 자리가 없으면 바 오른쪽 끝 위)을 누르면 「문서 선택」·「읽은 세션」 팝오버가 뜬다. 「문서 선택」은 지금 프로젝트의 문서와 목차를 보여 주는 모달을 열고, 모달 머리의 프로젝트 이름을 누르면 프로젝트 목록으로 바뀐다. 프로젝트를 고르면 그 프로젝트의 문서가 열리고 모달은 그 문서·목차 목록으로 돌아온다. 문서·목차를 고르면 닫힌다(「닫기」·바깥·Esc 로도). 「읽은 세션」은 그 목록만 모달로 연다. 섹션 배지를 누르면 그 섹션의 읽은 세션 모달이 열린다.
- **왼쪽:** 두 상자다. 「설계 프로젝트」는 기능 폴더 목록(읽힌 문서 수/전체, 워크트리 사본에서 온 폴더는 ▣)으로, 고르면 그 폴더에서 마지막으로 본 문서(없으면 읽는 순서의 첫 문서)가 열리고 상자는 접혀 고른 이름만 남는다. 「문서」는 고른 프로젝트의 문서로, 파일 이름 대신 제목으로 보이고 `index.html` 이 있는 폴더는 그 뷰어처럼 챕터(`01 개요 · 전제 · 용어`)로 묶어 읽는 순서대로 놓는다(그 목록에 없는 파일은 보이지 않는다). 문서마다 읽거나 검색한 세션 수가 붙고, 열린 문서 아래에 목차가 아코디언으로 펼쳐진다(섹션마다 읽은 세션 수, 누르면 그 섹션으로 스크롤하고 오른쪽이 그 섹션을 읽은 세션이 된다. 열린 문서를 다시 누르면 접힌다). 거르기 칸은 모든 프로젝트의 제목·챕터·파일 이름을 찾는다. 넓은 화면에서 「문서」 상자를 열고 닫은 것은 기억한다.
- **가운데:** 문서. Markdown 은 `marked`, 다이어그램은 `mermaid` 로 그린다(jsDelivr 에서 버전을 고정하고 SRI 로 받으며, 탭을 처음 열 때 불러온다). 문서 안 HTML 은 글자로 보이고, 상대 링크는 설계 폴더 안 문서·그림으로 풀린다. 섹션 제목마다 「세션 N · M회」 배지(0 이면 흐리게). 위쪽에 사본의 저장소·워크트리·브랜치·HEAD 와, 그 문서를 가리키는 외부 계획의 `design_commit` 이 HEAD 와 같은지가 보인다. 그림과 PDF 는 그대로 보인다.
- **오른쪽:** 배지를 누른 섹션(아니면 문서 전체)을 읽은 세션 목록 — read 비율·search 수·횟수·시각·티켓·지금 상태. 누르면 세션 상세로 간다. 목록 머리의 「숨기기」나 플로팅 바 필터의 「읽은 세션 보기」(설계문서 탭, 넓은 화면에서만 보인다)를 끄면 이 목록을 감추고 문서를 넓게 보며(기억한다), 섹션 배지를 누르면 다시 보인다.
- 배지·목록은 읽기만 센다(검색 적중은 세지 않고, 목록의 search 수로만 보인다). 기기별 저장값: `adash.design` (읽은 세션 보기, 거르기 글자, 마지막 문서와 프로젝트별 마지막 문서, 상자 열림).
- 세션 상세에 「참고한 설계 섹션」 절(문서별 섹션, 누르면 탭의 그 섹션), 코디네이터 상세의 티켓 의존 그래프 노드에 그 티켓 세션들이 많이 읽은 섹션 번호(`§5 · §3 · §4 +N`, 문서마다 같은 번호면 문서 제목을 앞에 붙임, 전체는 툴팁).

## 워크트리 리뷰 — QA 티켓별 워크트리를 VS Code 로 열어 리뷰

QA 에픽 하나(묶음)의 티켓마다 그 티켓의 Orca 워크트리를 모아 보여 주고, 한 번에 VS Code 로 열어 리뷰한 뒤 리뷰 결과를 볼트 스텝 노트에 남긴다. 「워크트리 리뷰」 탭(바의 겹친 판 아이콘)이 그린다.

- 「QA 단계」 선택으로 QA 드라이버 단계(또는 막힘)의 티켓만 거른다. 홈의 「QA 파이프라인」 「외 n건」이 이 값을 정해 연다.
- **묶음:** `qa_sets` 의 `{"epic", "project"}` 하나가 묶음이다. 티켓 = Jira `parent = <epic>` 의 이슈(5분마다, `jira_site`·`jira_email` + 환경 변수 `ATLASSIAN_API_TOKEN`. launchd 는 `~/.zshrc` 를 읽지 않으므로 없으면 대화형 zsh 에 한 번 물어 얻는다).
- **티켓에 붙는 것:** 폴더 이름에 그 키가 든 Orca 워크트리(메인·보관 제외), 파일 이름에 키가 든 스텝 노트(`<project>/progress.json` 의 step 경로)와 같은 프로젝트 폴더의 다른 노트, 키가 든 최근 테스트 실행, 그 워크트리에서 도는 에이전트.
- **저장소 줄:** 브랜치, 비교 베이스, 베이스보다 앞선 커밋 수·바뀐 파일 수·추가/삭제 줄, 뒤처진 커밋 수, 미커밋 파일 수. 베이스는 ① 그 브랜치 PR 의 base(`gh pr list --head`, 10분마다) ② `review_bases` 의 저장소별 값 ③ `main` 순이고, 로컬의 `origin/<베이스>`(없으면 `<베이스>`)와 비교한다. fetch 는 하지 않는다. git 수치는 30초마다, HEAD·베이스가 그대로면 캐시를 쓴다.
- **VS Code 로 열기:** 티켓의 워크트리를 실제 폴더 그대로, 저장소마다 새 창으로 연다(VS Code 앱의 `code -n <경로>`, 없으면 `open -n -a "Visual Studio Code" <경로>`, `review_first` 저장소가 먼저). 임시 `.code-workspace` 로 묶어 열면 창이 워크트리가 아닌 다른 곳처럼 보여서 바꿨다. 요청의 Host 가 루프백이고 `X-Forwarded-For` 가 없을 때만 된다 — 이 맥에서 연 페이지만. tailnet 기기(`tailscale serve` 경유)는 403 이고 버튼이 꺼져 보인다.
- **PR 후 머지:** Jira 「진행 중」 이고 워크트리가 있는 티켓에 버튼이 보인다. 확인 창을 거쳐 서버가 `ship_prompt` 템플릿의 `{{key}}`·`{{summary}}`·`{{jira_url}}`·`{{jira_status}}`·`{{assignee}}`·`{{epic}}`·`{{project}}`·`{{vault}}`·`{{step_note}}`·`{{notes}}`·`{{repos}}`(저장소마다 워크트리·브랜치·베이스·PR·앞선/뒤처진 커밋 한 줄, `review_first` 가 먼저)를 채워 `orca orchestration worker-start --spec` 으로 감독 워커를 띄운다. 워커 자리는 묶음의 `ship_place`(티켓 워크트리 밖 — 워커가 마지막에 그 워크트리들을 지울 수 있게), 에이전트·모델은 `ship_agent`·`ship_model`(기본 `claude`·`opus`), 탭과 태스크 이름은 `<키> 반출`. Run 은 묶음마다 목표가 `<에픽> 티켓 반출 (대시보드)` 인 것 하나를 찾아 재사용하고, 없으면 만든다. 그 Run 을 지켜보는 코디네이터가 없으므로 무엇을 하고 언제 멈출지는 프롬프트가 정한다. 티켓 줄에 그 태스크 상태(반출 시작 중·대기·중·완료·실패, 시작 실패 사유는 툴팁)가 칩으로 보이고, 끝나지 않은 태스크가 있으면 버튼이 꺼진다. 루프백 제한은 없다 — 이 맥에 창을 띄우는 일이 아니다.
- **리뷰 기록:** 「리뷰 완료」는 스텝 노트 frontmatter 에 `review: done`, `review_sha:` (저장소별 지금 HEAD 9자리), `review_at:`, 드라이버 묶음이면 `review_round:` (그때의 회차)를 쓴다. 「리뷰 취소」는 이 필드를 지운다. 워크트리 HEAD 가 리뷰 뒤에 바뀌면(반출 전 리베이스 등) 서버가 `review_sha` 를 지금 HEAD 로 따라 고친다 — 「리뷰 후 변경」으로 되돌리지 않는다. 드라이버가 재오픈으로 더 뒤 회차를 기동하면 「재오픈 후 리뷰 대기」로 바뀐다 (`review_round` 가 없는 옛 기록은 `review_at` 이 그 회차 시작일보다 앞서거나, 같은 날이고 노트가 그 뒤로 쓰이지 않았으면). 노트의 `updated` 는 건드리지 않는다(상태 표시이지 내용 수정이 아니다). 커밋은 하지 않는다.
- **Jira 상태:** 티켓 머리의 칩과 묶음 머리의 상태별 수로 보인다. 시작 전·진행 중·개발 완료·QA 준비 완료·QA 완료로 나누는데, 개발 완료·QA 준비 완료는 Jira 범주가 진행 중과 같은 `indeterminate` 라 이름으로 가른다(모르는 이름은 범주로: `new` → 시작 전, `done` → QA 완료, 나머지 → 진행 중). 개발 완료는 테두리만, QA 준비 완료는 채운 칩이다. 위쪽 거르기 단추 줄 하나에 리뷰 상태와 Jira 상태가 구분선을 두고 함께 있고, 하나만 고른다(`adash.wt` 에 저장).
- **상태:** 워크트리 없음 → `none`, 기록 없음 → `pending`(리뷰 대기), 기록한 sha 가 모든 저장소의 지금 HEAD 와 같으면 `done`, 하나라도 다르면 `changed`(리뷰 후 변경 — 저장소 줄에도 표시). `changed` 는 파일에 쓰지 않고 매번 계산한다.

**QA 드라이버 진행·제어.** 묶음에 `watch`(상태 디렉터리)가 있으면 [qa-ticket-driver](https://github.com/s12171934/qa-ticket-driver) 스킬의 상태 계약(`exports/state-contract.md`)대로 티켓마다 단계를 읽어 9단계 트랙(선별 → 워크트리 → 분석 → 구현 → 검토 → 커밋 완료 → 반출 승인 → 반출 → 정리)으로 보인다. 옛 워처의 상태 디렉터리(`claimed/ handoffs/ ready/ blocked/`)도 같은 규칙으로 읽힌다.
- 티켓 줄: 단계 트랙(번호 아래 단계 이름, 툴팁에 그 단계의 뜻과 진입 시각, 트랙 옆에 「n/9 단계 · 다음: 누가 무엇을 하는지」 — 사용자 승인이 다음이면 경고색), 회차(재오픈), 막힘과 그 사유, 반출된 PR 링크, 코디네이터·워커 칩(그 Orca 터미널의 세션으로 이동, 닫혔으면 흐리게). 드라이버 묶음(`watch` 아래 `tickets/` 가 있음)이면 저장소 줄은 티켓 워크트리의 채워진 서브모듈에서 만든다.
- 묶음 머리: 「QA 드라이버 9단계란?」 펼침 상자(단계마다 뜻과 다음 단계로 넘기는 주체, 막힘·회차·제외 설명. 열림 상태는 `adash.qalegend` 에 저장), 단계별 티켓 수, 그리고 이름·프롬프트·precheck 에 에픽 키가 든 Orca 자동화마다 켜짐/꺼짐 · 스케줄 · 다음/마지막 실행 · 최근 실행 8회 점과 「켜기/끄기」·「지금 실행」(1분마다 갱신).
- 「리뷰 완료 · 반출 승인」(드라이버 묶음의 `committed` 티켓 — 코디네이터가 `ready/` 를 쓴 뒤): 리뷰를 기록하고 `qa-driver approve` 로 `approved/<키>.md` 를 남겨 코디네이터 터미널에 알린다(닫혔으면 그 워크트리에 반출용 코디네이터를 새로 띄운다). 그 전 단계(코디네이터가 아직 워크트리를 바꾸는 중)에는 「리뷰 완료」가 비활성이고 서버도 409 로 거절한다. `committed` 를 지난 뒤(승인·반출·정리)에는 리뷰만 기록한다. 옛 워처 묶음은 대신 「PR 후 머지」를 쓴다.
- 「PR 머지」(드라이버 묶음의 `delivered` 티켓, 아직 지시 전): `qa-driver merge` — `merge/<키>.md` 에 PR 주소를 남기고 코디네이터에게 의존 저장소부터 머지하라고 알린다(닫혔으면 새로 띄운다). 머지할 수 없으면 코디네이터가 `blocked/` 로 남긴다. 지시 뒤에는 「머지 지시됨」 표시만 남고, PR 이 모두 머지되면 드라이버 회차가 정리한다.
- 「워크트리 정리」(`committed`·`approved`·`delivered`): 먼저 `qa-driver cleanup --dry-run` 결과를 보여 주고 확인을 받은 뒤 지운다. 커밋하지 않은 변경이나 push 되지 않은 커밋이 있으면 멈춘다(강제 정리는 화면에 없다).
- 티켓 줄 「⋯」: 「코디네이터 재기동」(열린 터미널이 없고 반출 전일 때, `qa-driver restart` — 기록된 브리프로 다시 띄움). 공용 코디네이션 워크트리에서 돌던 옛 워처 티켓에도 보인다. 터미널 닫기·드라이버 제외는 화면에 없다(`qa-driver close`·`ignore` 로 한다).
- 워처 줄(`watch` 가 있는 묶음): 옛 워처면(에픽을 부르는 자동화 중 프롬프트가 `qa-driver` 를 부르는 것이 없음) 「옛 워처」 표시와 「드라이버로 이관」 — `qa-driver adopt --check` 로 빠진 `config.env` 키를 물어(추정값: `QA_REPO` 는 CLI, `JIRA_SITE` 는 서버의 `jira_site`) 채운 뒤 `adopt` 로 자동화의 precheck·프롬프트를 바꾼다. 이미 처리 중인 티켓은 그대로 두고 이후 회차부터 새 흐름을 탄다. 공용 코디네이션 워크트리(`config.env` `QA_COORD_WORKTREE`)와 열린 에이전트 터미널 수, 「끝난 코디네이터 닫기 (n)」(Jira 가 개발 완료 이후이거나 반출·정리가 끝났고, 열린 터미널의 세션이 모두 쉬고 있는 티켓). 모든 하위 티켓이 QA 완료면 「QA 종료 처리」 — `retire --dry-run` 결과를 보여 확인을 받은 뒤 `retire`(자동화 끄기, 공용 코디네이션 워크트리의 터미널을 닫고 지움, `retired` 표시). 검토 전 티켓이 남으면 멈춘다(강제 종료는 화면에 없다).
- 묶음 머리 「QA 통계」 펼침 상자(열림 상태는 `adash.qastats`): ① 요약 — QA 완료 n/전체(진행 바), 재오픈 티켓 수·비율, 평균 회차(드라이버가 잡은 티켓), 드라이버 기동 티켓 수, 막힘 수. ② 일별 추이 — 최근 14일, 날마다 기동한 회차(신규 = 1회차, 재오픈 = 2회차 이후, `claimed/<키>` 의 줄마다)와 커밋 완료(`ready/` 시각. 정리는 자동화가 하므로 완료로 세지 않는다) 수. 완료는 티켓의 마지막 회차만 남아 앞 회차의 완료는 세지 않는다. ③ 코드 변경 규모 — 워크트리가 남은 티켓의 저장소별 바뀐 파일·추가/삭제 줄 합과 PR 수(정리된 티켓은 빠진다). 모두 화면에서 `/api/reviews` 로 계산한다.
- 제어는 스킬의 CLI(`prefs.json` `qa_driver`, 기본 `~/.claude/skills/qa-ticket-driver/bin/qa-driver`)를 부른다. 규칙은 스킬 한 곳에 있다.

## 보안

- **인증이 없다.** 바인드한 주소(루프백, tailnet 등)에 닿는 클라이언트는 모두 신뢰한다. 공용 네트워크 주소에 바인드하지 않는다.
- `Host` 헤더가 바인드 주소가 아닌 요청은 거부한다 (DNS rebinding 방지).
- 브라우저 요청은 `Origin` 이 `--origin`(과 로컬 출처) 밖이면 거부한다. 그래야 사용자가 연 다른 웹페이지가 세션 로그를 읽거나 터미널을 닫지 못한다. 페이지 자체는 공개라 누구나 열 수 있지만, 그 사람 브라우저는 그 사람 자신의 로컬 주소를 부를 뿐이다.
- 세션 로그 내용이 화면에 그대로 보인다. 화면 공유·원격 접근 시 주의한다.
- 서버에 닿는 클라이언트는 「새 에이전트」로 그 Mac 에 워크트리를 만들고 에이전트를 띄우며 프롬프트를 넣을 수 있다(에이전트는 사용자의 권한 설정 그대로 돈다). tailnet 에 바인드했다면 tailnet 의 기기 모두가 그렇다.

## 공개 면

다른 도구·자동화가 의존해도 되는 것은 아래뿐이다. 나머지(웹 UI 가 쓰는 `/api/*` HTTP 엔드포인트 등)는 내부용이라 예고 없이 바뀔 수 있다.

- `aplan` CLI 와 그 기록 형식 (`~/.agent-plans/*.jsonl`)
- `server/server.py` 실행 옵션과 `server/launchd/install.sh` 환경 변수
- 테스트 진행 파일 형식 — `/private/tmp/agent-test-progress/` 에 실행 하나당 JSON 하나를 원자적으로(임시 파일에 쓴 뒤 rename) 갱신한다. 필드: `label` `kind` `phase` `detail` `total` `done` `passed` `failed` `pending` `started_at` `updated_at` `eta_s` `log` `owner` `terminal` `session_id`

- 프로젝트 진행 파일 형식 — `exports/project-progress.schema.json` (JSON Schema). 서버는 `--projects-dir` 아래에서 읽어 위 「프로젝트 진행 API」로 준다. 프로젝트마다 `progress.json` 하나에 흐름 단계(stage)와 단계마다 그 안의 작업(step — 날짜·상태 scheduling·pending·active·done·failed)만 담고, 단계 상태·기간·작업 수·진행률 같은 파생값은 대시보드가 계산한다.
