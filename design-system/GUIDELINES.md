# 디자인 시스템 규칙

이 문서는 `design-system/` 과 그것을 쓰는 페이지(`frontend/`)가 **반드시** 지켜야 하는 규칙이다. 지금 있는 컴포넌트뿐 아니라 앞으로 추가하는 모든 컴포넌트·재질·토큰에 똑같이 적용한다. 규칙 번호(예: `M1`)는 검사 스크립트의 출력과 같다.

- 변경을 올리기 전에 `python3 scripts/check-ds.py` 가 통과해야 한다 (스크립트가 볼 수 있는 규칙을 검사한다. 🔍 표시).
- 스크립트가 못 보는 규칙은 아래 「완료 기준」의 손 점검으로 확인한다.
- 규칙을 바꿀 때는 이 문서, 검사 스크립트, README 를 함께 고친다.

## 1. 레이어와 의존 방향

```
foundations/  →  materials/  →  components/  →  페이지(frontend/)
(팔레트·모양·런타임)  (표면이 어떻게 보이나)  (무엇이 있나)      (어디에 무엇을 놓나)
```

- **L1** 의존은 화살표 방향으로만 흐른다. 아래 레이어는 위 레이어를 모른다.
  - 컴포넌트는 페이지의 id·클래스(`#dock`, `.card` …)나 페이지 전역 변수를 참조하지 않는다.
  - 재질은 컴포넌트를 모른다. 토큰 값만 정한다.
- **L2** 페이지가 디자인 시스템에 넘기는 값은 문서에 적힌 변수뿐이다. 지금은 `--dock-inset-top` 하나다. 새로 필요하면 그 컴포넌트의 CSS 주석과 README 에 계약으로 적는다.
- **L3** 페이지 CSS(`app.css`)는 `ds.css` 뒤에 로드하고, 디자인 시스템 파일을 고치지 않고 덮어써서 조정한다. 같은 조정이 두 화면 이상에서 필요하면 디자인 시스템으로 올린다.

## 2. 색 (foundations/tokens.css)

- **C1** 🔍 컴포넌트 CSS 에 색 리터럴(`#hex`, `rgb()`, `hsl()` …)을 쓰지 않는다. 색은 팔레트 토큰(`--accent`, `--ok`, `--on-accent` …)이나 재질 토큰으로만 쓴다.
- **C2** 팔레트 토큰은 단색 hex 다. 「색 편집」 색 선택기와 SVG 선이 그 값을 그대로 읽기 때문이다. 반투명은 토큰에서 `color-mix()` 로 파생한다.
- **C3** 새 팔레트 토큰은 라이트·다크 두 블록에 모두 정의한다. 사용자가 바꿀 수 있어야 하는 색이면 `foundations/theme.js` 의 `THEME_VARS` 와 `PALETTES` 의 모든 세트에 함께 넣는다.
- **C4** 상태 색은 의미로 쓴다: `--run`·`--ok` 진행, `--warn` 대기·결정, `--bad` 오류·응답 없음, `--done` 완료, `--idle` 유휴. 장식 목적으로 상태 색을 쓰지 않는다. 채워진 색 위의 글자와 아이콘은 `--on-accent` 로 쓴다.

## 3. 재질 (materials/)

리퀴드글래스는 디자인 시스템 본체가 아니라 **재질**의 하나다. 컴포넌트는 "표면이 있다"만 알고, 그 표면이 유리인지 매트인지는 재질이 정한다.

- **M1** 🔍 모든 재질은 **재질 계약**의 토큰을 전부 정의한다. 계약의 기준은 `materials/glass.css` 의 라이트 블록이고, 머리말 주석에 토큰 목록이 있다.
  - 다크는 라이트와 다른 값만 덮어쓴다.
  - 계약에 없는 토큰을 한 재질에서만 만들지 않는다.
  - 재질 파일은 `data-material="<이름>"` 으로 선택된다.
- **M2** 🔍 컴포넌트와 페이지는 표면·컨트롤·막대·차트를 계약 토큰으로만 그린다.
  - `backdrop-filter` 는 언제나 `var(--surface-blur…)`, 흰 하이라이트·광택·그림자 리터럴은 쓰지 않는다.
  - 표면: `background: var(--surface-sheen), var(--surface…)`, `border-color: var(--surface-edge)`, `box-shadow: var(--surface-hi), var(--surface-shadow…)`
  - 컨트롤: `--control-*`, 막대: `--bar-*`, 차트: `--chart-*`, 모달 뒤: `--scrim-blur`
- **M3** 새 시각 효과가 필요하면 먼저 계약에 토큰을 추가한다. 추가할 때는 아래를 한 번에 한다.
  1. 모든 재질에 값을 넣는다. 매트처럼 효과가 없는 재질은 `0 0 transparent`, `none`, `0px` 같은 "없음" 값을 넣는다.
  2. `glass.css` 머리말의 계약 주석을 고친다.
  3. 그다음에 컴포넌트에서 쓴다.
- **M4** "없음" 값은 그 속성의 문법에 맞게 쓴다. 쉼표로 이어지는 `box-shadow` 에는 `none` 대신 `0 0 transparent` 를 쓴다(`none, …` 은 무효). 배경 이미지는 `none`, 길이는 `0px` 이다.
- **M5** 재질은 `<html data-material>` (`theme.js` 의 `applyMaterial`, 저장 키 `adash.material`)으로 고른다. 어떤 요소에든 `data-material` 을 붙이면 그 하위 트리만 다른 재질이 된다. 컴포넌트는 특정 재질을 가정하지 않는다.
- **M6** 새 재질은 `materials/<이름>.css` 하나로 만들고 다음을 함께 한다.
  - `ds.css` 에 import 를 추가한다.
  - `theme.js` 의 `MATERIALS` 에 이름을 등록한다.
  - `scripts/check-ds.py` 의 `MATERIALS` 에 추가한다.
  - `sw.js` 의 `SHELL` 에 넣는다.

## 4. 컴포넌트 형태

- **E1** 🔍 구조(자식 요소를 만든다)나 동작(이벤트, 저장)이 있는 컴포넌트는 커스텀 엘리먼트 `<ds-이름>` 이다. 파일 이름은 `components/<이름>/ds-<이름>.js` 이고, 그 안에서 `customElements.define('ds-<이름>', …)` 한다.
- **E2** 🔍 light DOM 만 쓴다(`attachShadow` 금지). 페이지 CSS·스크립트가 안쪽 요소를 그대로 선택하고, 재질 토큰이 상속으로 닿아야 하기 때문이다.
- **E3** API 는 속성(attribute)이다.
  - 상태는 속성으로 받고 CSS 의 속성 선택자로 그린다. 예: `ds-pill[state="run"]`
  - 속성 값이 바뀌어도 반영되어야 하면 `observedAttributes` 로 다시 그린다.
  - 내용은 자식(텍스트, 슬롯이 아닌 실제 자식 요소)으로 받는다.
- **E4** `connectedCallback` 은 여러 번 불려도 안전해야 한다(다시 붙어도 중복 생성 없음).
  - 정의되기 전에 이미 페이지에 있던 마크업도 업그레이드되면 정상 동작해야 한다.
  - 네트워크 요청을 하지 않고, 엘리먼트 밖 문서를 바꾸는 일은 최소로 한다(예외: `ds-dock` 은 팝오버를 `<body>` 끝에 둔다. 이유는 주석에 있다).
- **E5** 겉모습만 있는 컴포넌트(배지, 버튼, 막대 …)는 클래스다. 클래스형도 폴더와 CSS 파일은 똑같이 둔다(F1).
- **E6** 첫 페인트 전에 정해져야 하는 상태(테마, 재질, 바 위치)는 `<head>` 의 일반 스크립트(`foundations/theme.js`, `*-boot.js`)가 정한다. 모듈(`ds.js`)은 지연 실행되므로 레이아웃을 정하지 않는다.
- **E7** 기기별 저장은 `localStorage` 의 `adash.` 접두사 키만 쓰고, 읽기·쓰기는 `try/catch` 로 감싼다. 새 키는 README 의 저장값 목록에 적는다.

## 5. 파일과 등록

- **F1** 🔍 컴포넌트 하나 = 폴더 하나: `components/<이름>/<이름>.css` 와 `<이름>.html`(마크업 계약, 6장), 필요하면 `ds-<이름>.js`, 첫 페인트용이면 `<이름>-boot.js`. 그 밖의 스크립트를 두지 않는다.
- **R1** 🔍 `ds.css` 의 import 순서는 `foundations/tokens.css`, `foundations/base.css`, 재질들, 컴포넌트들이다. 순서가 곧 캐스케이드 순서다. 다른 컴포넌트를 덮어쓰는 컴포넌트는 그 뒤에 둔다.
- **R2** 🔍 엘리먼트 스크립트는 `ds.js` 에 import 한다.
- **R3** 🔍 모든 파일을 `frontend/sw.js` 의 `SHELL` 에 넣고, 캐시 이름(`adash-shell-vN`)을 올린다.
- **R4** 미리보기(`index.html`)는 `ds.css` 의 컴포넌트 목록과 각 `<이름>.html` 로 저절로 만들어진다. 미리보기에 컴포넌트를 손으로 쓰지 않는다.
- **R5** 🔍 README 의 컴포넌트 표에 한 줄을 넣는다(API, 파일).

## 6. HTML (마크업 계약)

CSS 와 스크립트만으로는 컴포넌트를 바르게 쓸 수 없다. 어떤 요소에 어떤 클래스·속성·자식을 두는지가 같이 정해져야 한다. 그래서 컴포넌트마다 `<이름>.html` 이 그 컴포넌트의 **마크업 계약**이다.

- **H1** 🔍 모든 컴포넌트는 `components/<이름>/<이름>.html` 을 둔다. 엘리먼트형이면 그 태그(`<ds-이름>`)의 예시를 반드시 포함한다.
- **H2** 🔍 파일은 주석으로 시작한다. 첫 줄은 `<!-- <이름> — 무엇인가.` 이고, 이어서 다음을 적는다.
  - 받는 마크업의 모양: 요소, 클래스, 필수·선택 속성과 값의 목록, 자식
  - 지켜야 할 접근성 속성
  - 엘리먼트가 스스로 만드는 부분(쓰지 말아야 할 것)

  그 뒤에 대표 상태를 모두 보여 주는 예시 마크업을 둔다.
- **H3** 🔍 마크업만 둔다(`<script>`·`<style>` 금지). 모양은 `.css`, 동작은 `ds-*.js` 에 있다. 예시의 인라인 스타일은 페이지가 원래 인라인으로 주는 값(막대 너비, 칩 색 `--c`)이나 미리보기에서 제자리에 펼쳐 보이기(`position: static`)에만 쓴다. 스크립트 API 가 있는 컴포넌트(툴팁, 토스트, 대화상자)는 미리보기에서 눌러 볼 수 있게 예시에 인라인 핸들러(`onclick` 등) 한 줄을 둘 수 있다.
- **H4** 페이지는 계약의 구조를 그대로 쓴다.
  - 계약에 없는 감싸는 요소나 다른 자식 순서를 쓰지 않는다.
  - 상태는 계약의 클래스·속성 이름으로만 표현한다.
  - 페이지에만 필요한 클래스(예: 색 변형)를 덧붙이는 것은 괜찮다.
  - 계약이 부족하면 페이지에서 우회하지 않고 계약(`<이름>.html`)부터 고친다.
- **H5** 의미에 맞는 요소를 쓴다: 누르는 것은 `<button>`, 이동은 `<a href>`, 켜고 끄는 것은 `<label>` 안의 `<input type="checkbox">`. `<div>` 에 클릭을 붙이지 않는다.
- **H6** 마크업 계약을 바꾸는 변경(클래스·속성 이름, 구조)은 그 컴포넌트를 쓰는 페이지 마크업과 템플릿(`app.js`)을 같은 변경에서 함께 고친다.

## 7. 선택자와 캐스케이드

- **S1** 🔍 컴포넌트 CSS 에 id 선택자를 쓰지 않는다. 태그(`ds-이름`), 클래스, 속성 선택자만 쓰고, 특이도는 필요한 만큼만 높인다. 페이지가 같거나 높은 특이도로 덮어쓸 수 있어야 한다.
- **S2** 🔍 `!important` 를 쓰지 않는다(예외: `base.css` 의 `prefers-reduced-motion`).
- **S3** 크기·간격·모서리는 토큰(`--radius`, `--dock-sz` …)이나 컴포넌트 안의 고정값으로 정한다. 같은 값을 둘 이상의 컴포넌트가 쓰기 시작하면 토큰으로 올린다.

## 8. 아이콘

- **I1** 🔍 아이콘은 `components/icon/icons.svg` 의 `<symbol id="이름" viewBox="0 0 24 24">` 이다. 선 아이콘이고, 도형에 `fill`·`stroke`·`style`·`class` 를 넣지 않는다(icon.css 가 `currentColor` 로 그린다).
- **I2** 쓸 때는 `<ds-icon name="이름">` 이다. 크기와 색은 놓는 쪽이 정한다(`… svg { width }`, `color`).

## 9. 접근성과 동작

- **A1** 아이콘만 있는 버튼에는 `aria-label` (읽을 이름)과 `data-tip` (호버 이름)을 둘 다 둔다.
- **A2** 키보드 포커스는 `:focus-visible` 로 보이게 한다. 체크박스를 숨긴 토글은 `:has(input:focus-visible)` 로 표시한다.
- **A3** 애니메이션은 `base.css` 의 키프레임(`pulse`, `blink`)과 `transition` 만 쓴다. `prefers-reduced-motion` 에서 꺼진다. 상태를 깜빡임만으로 전하지 않는다(라벨이나 모양도 함께).
- **A4** 누를 수 있는 것은 최소 28px 이다(바 버튼은 `--dock-sz`). 손가락 기기에서는 `--tap` 을 따른다(B3).
- **A5** 폭 500px 이하(휴대폰)에서도 한 화면에 들어가야 한다. 넘치면 그 컴포넌트 CSS 안에 미디어 쿼리를 둔다(10장).
- **A6** 바에서 여는 팝오버는 `.dock-pop` 으로 만들고 `hidden` 으로 열고 닫는다. `.dock-pop` 은 한 그룹이라, 하나가 열리면 나머지는 저절로 닫힌다(ds-dock.js). 팝오버끼리 서로를 닫는 코드를 페이지에 따로 쓰지 않는다.

## 10. 반응형과 모바일

폭은 세 단계, 입력 방식은 폭과 따로 본다. 값은 `foundations/tokens.css` 의 layout 블록이 기준이다.

| 단계 | 미디어 쿼리 | 무엇이 바뀌나 |
| --- | --- | --- |
| 태블릿 | `(max-width: 900px)` | 나란히 놓인 판이 위아래로 쌓인다 |
| 좁은 화면 | `(max-width: 700px)` | 그리드가 한 열로 접히고, 헤더가 줄고, `--gutter` 가 12px 이 된다 |
| 휴대폰 | `(max-width: 500px)` | 바는 런처 알약 + 바텀시트가 되고, 컨트롤이 한 줄에 들어가도록 줄어든다 |

- **B1** 🔍 `@media` 의 폭 조건은 위 세 값의 `max-width` 만 쓴다. 다른 폭이 필요해 보이면 레이아웃을 그 세 단계에 맞춘다. 컨테이너 쿼리(`@container`)는 판 자신의 폭을 보므로 이 규칙 밖이다.
- **B2** 입력 방식은 폭이 아니라 `(pointer: coarse)`(손가락), `(hover: none)`(호버 없음)으로 가른다. 좁은 데스크톱 창과 휴대폰을 같은 것으로 보지 않는다.
- **B3** 손가락 기기에서 누르는 것은 `--tap`(coarse 일 때 36px) 높이를 받는다. 모양을 키우기 어려운 작은 알약 버튼(`.act`)은 보이지 않는 `::before` 로 누르는 영역만 넓힌다.
- **B4** 손가락 기기의 글 입력란은 16px 이상이다(그보다 작으면 iOS 가 화면을 확대한다). `base.css` 가 정하므로 컴포넌트·페이지가 coarse 에서 입력란 글자를 줄이지 않는다.
- **B5** 페이지는 폭 390px 에서 가로로 스크롤되지 않는다. 화면보다 넓을 수 있는 것은 자기 안에서 가로로 스크롤한다: 표는 `.tscroll` 로 감싸고, `.seg` 는 스스로 스크롤한다. 휴대폰의 바는 한 줄에 넣지 않고 런처 알약과 바텀시트로 바뀐다.
- **B6** 호버로만 알려 주는 정보는 호버 없는 기기에서 다른 길(라벨, `aria-label`, 누르면 열리는 상세)이 있어야 한다. 바 버튼의 호버 이름은 `(hover: none)` 에서 끄고 `aria-label` 이 대신하며, 휴대폰 시트에서는 같은 `data-tip` 이 행의 이름으로 보인다.
- **B7** 페이지 가장자리 여백은 `--gutter` 와 `env(safe-area-inset-*)` 중 큰 값이다(노치·홈 막대).

## 11. 완료 기준

새 컴포넌트나 토큰·재질 변경은 아래를 모두 만족해야 끝난 것이다.

1. `python3 scripts/check-ds.py` 통과
2. `<이름>.html` 에 바뀐 구조와 상태가 모두 들어 있다
3. 미리보기(`/ds/`)에서 **라이트·다크 × 유리·매트** 네 조합을 눈으로 확인
4. 폭 390px 에서 가로 스크롤 없이 확인하고, 손가락 기기(개발자 도구의 기기 모드)에서 누르는 영역과 입력란 확대가 없는지 확인 (미리보기 위쪽에 지금 폭 단계가 보인다)
5. 기존 화면이 바뀌지 않아야 하는 변경이면, 변경 전후의 계산된 스타일을 비교해 의도한 차이만 남았는지 확인
6. README 표와 이 문서(규칙이 늘었다면)를 갱신
